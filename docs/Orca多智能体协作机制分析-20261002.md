## 0. 一句话结论

**Orca 的协作层不是"更多工具"，是一套"权威从哪来、什么时候算结束"的判据。**

MemoryOS 侧已经有完整的协作**词汇表**（12 个 `task_*` 工具，覆盖 gate / delegate / verify / supersede / heartbeat / release / block / reopen / next），缺的不是工具，而是**把它们串起来的权威锚点**与**"缺席不授权"的安全底线**。

这解释了为什么 Dispatch 语义（批次 1）方向是对的——它补的正是那个锚点。

**但真正没被抄到的、也是价值最高的一条是**：

> Only positive proof of exit authorizes stop, abandon, or retry; only an accepted settlement authorizes release. **Every other observation, absence included, is a checkpoint.**

MemoryOS 目前的守护进程**正在用"沉默"授权回收**（§4 P0-1）。

## 1. Orca 的协作模型

### 1.1 四对象分离

| 对象 | 定义（Orca 原文） | 职责边界 |
|---|---|---|
| **Run** | a durable namespace and coordinator inbox | **不调度、不放置** worker；只是命名空间 + 收件箱 |
| **Task** | work | 工作单元 |
| **Dispatch** | **one authoritative Task attempt** | 授权的唯一来源 |
| **Worker** | 被放置的 agent 终端 | 执行体 |

关键：**attempt（尝试）是一等公民**。同一 Task 可以有第 2 次尝试，第 1 次就被*取代（superseded）*而非*删除*。

### 1.2 权威规则

> Lifecycle authority comes from the active Dispatch — **not a terminal title, copied ID, old database row, provider transcript, or visible pane.**

五个排除项是重点：**终端标题、抄来的 ID、旧数据库行、provider 转录、可见面板**——全是"看起来像权威"的东西。Orca 明确把它们全部降级为非权威。

推论（原文）：*Never reconstruct, translate, or broaden those arguments.* 参数不能自行翻译或放宽。

### 1.3 角色五分类

| 场景 | 角色 | 路由 |
|---|---|---|
| 用户要求监督/跟踪完成/协调 DAG | Coordinator | 走受监督循环 |
| 提示里带 live preamble（Task + Dispatch ID） | Dispatched worker | 遵守 worker 义务 |
| 用户要求移交所有权但不要求监督 | Handoff owner | 用 `orca-cli`，**不建 Run/Task/Dispatch，不监控完成** |
| 消息带 legacy 权威标签 | Compatibility operator | 先读 legacy 契约再改生命周期 |
| 无 preamble、无监督 | Ordinary terminal agent | **不发生命周期消息** |

要点：**"移交"≠"监督"**。移交是所有权转移，监督是协调职责，Orca 用角色表强行分开。

### 1.4 存活三态与"缺席不授权"

| 态 | 含义 | 授权 |
|---|---|---|
| `live` | 有正向存活证据 | 可以等 |
| `unverifiable` | **缺席**（无状态行、联系丢失、状态陈旧）| **什么都不授权** |
| `exited` | 正向退出证据 | 可 stop / abandon / retry |

原文明说：*A live terminal can still hold a dead or stuck agent.*（终端活着 ≠ agent 活着）
且：*contact loss is not process death*（联系丢失 ≠ 进程死亡）。

**层层设防**：`worker-list` 的 `projection.liveness` 是**机队判据**；`worker-show` 的 `observation.status` **只代表 PTY**。两者冲突时以机队判据为准——**除非**机队行是 `unverifiable` 且原因指向本客户端的能力缺口（`missing_status` / `host_unavailable` / `capability_unsupported`），此时执行主机给出的判据反超。

### 1.5 worker_done 契约（exactly once）

- **恰好一次**，从被派遣的终端发出
- **三句话摘要**：改了什么 / 发现了什么 / 剩下什么
- **两个生命周期 ID**（Task + Dispatch）
- **显式 `--outcome succeeded|failed`**
- *Never encode failure only in prose.*（禁止只在散文里编码失败）
- 发完即 idle：**不轮询、不关自己的终端、不开始无关工作**
- 用户后续直接指令 = **新的用户自有工作**，**不得复用已结算的生命周期 ID**

### 1.6 心跳、ask、fence

- 心跳**只证存活，不证完成**；被 `ask` / `check --wait` 阻塞期间不用发（那些调用本身就是存活信号）
- **ask**：coordinator 必须回答的阻塞提问。超时**保留同一个 pending question**，用原 `message_id` 恢复，**不得重复提问**
- **consumer_fenced**：worker 得知"自己已被取代"的**唯一途径**。原文：*An empty check never means you were replaced; `consumer_fenced` is the only way you learn that.*

### 1.7 消息与门

- `send` 成功只证明**持久入队**；wake / nudge 是**尽力而为的关注提示**，不证明对方读了、开始了、接受了
- 协调者 `check` 返回**最老的一批 FIFO Delivery（≤50 条）**，**同一批重放到 ack 为止**。类型过滤只决定"何时唤醒"，**不授权跳过更老的可执行邮件**
- **空等待 / 超时是检查点，不是失败**
- 连续三次空等 → 停止盲等，改用 `worker-list` 枚举，按每行的 `projection.nextAction`（**字面可执行 argv**）行动；`nextAction = none` 表示**没有 argv 可跑**——**缺席永远不换来 argv**
- **gate** 只用于协调者拥有的 **Task-DAG 决策**（`gate-create` / `gate-resolve` / `gate-list`）。原文：*Do not create a gate merely to answer a worker's `ask`.*

### 1.8 完成后三选一（强制枚举）

成功/失败报告被接受后，**立刻且只能做一件**：

1. **复用**同一 agent 终端做下一个 Dispatch
2. `worker-retain` 记录用户要求的保留
3. `worker-release`

且协调轮**不得结束**，直到 `worker-list --run <id> --terminal-state reclaimable` 返回空。原文：**Release is post-settlement cleanup, not cancellation.**

### 1.9 恢复与幂等

- 恢复表按**已证明状态**给安全动作；`outcome_unknown` → **先检查**，再显式选 `worker-stop` 或 `worker-abandon`
- **同一 Task 连续 3 次失败 → 熔断**，Task 置 failed；*Do not route around that boundary with a new Run*（不许用新 Run 绕过）
- `--retry-request <id>`：**复用操作身份**，让 Orca 重放/合并/恢复，而不是起副本；配合 `request-show` 查 `completed / pending / absent`
- `worker-abandon` **只隔离编排**，接受资源可能仍活着；**不做任何远程/进程/文件动作**
- `--on <environment>` 起的 worker 在你用 `--include-remote` 枚举前一直读 `unverifiable`

### 1.10 Task-spec 五要素

每个 Task spec 必须自包含并写明：

| 要素 | 内容 |
|---|---|
| **Target** | 范围内的文件/组件/环境 |
| **Change** | 要产出的具体结果 |
| **Constraints** | 不变量、兼容规则、禁改边界 |
| **Ownership** | 本 worker 可编辑什么、协调边界在哪 |
| **Observable acceptance** | 证明完成的测试/输出/证据 |

### 1.11 Review ownership

> A review-only `worker_done` authorizes synthesis of findings, **not coordinator file edits.**

只做审查的完成报告，只授权"综合结论"，**不授权协调者改文件**。修复要另行派遣或移交——除非用户明确指派给协调者。

### 1.12 文档分片加载

kernel 约 13KB 常驻；7 篇 references **按"动作门"加载**（如"失败/停止/未知尝试 → `recovery-and-cleanup.md`"）。这是**上下文的按需 paging**，本身就是一条工程启发。

### 2.3 租约回收：两阶段 reaper（**关键实证**）

`daemon.js:688-754` `reapExpiredLeases`：

| 阶段 | 条件 | 动作 |
|---|---|---|
| ① 贴条 | `status='running'` 且 `lease_expires_at < now` 且 `lease_notice_at IS NULL` | 写 `lease_notice_at`，卡**保持 running、锁保留**，事件 `lease_expired`（694-700）|
| ② 放回 | 贴条超过 `MEMORYOS_LEASE_GRACE_HOURS`（默认 **24h**）无人理 | **一笔事务**：任务头 CAS `in_progress`→`pending` + 卡 `status='ready', assignee=NULL, claim_lock=NULL`（704-737）|

**判读**：MemoryOS 有 **grace 缓冲**（贴条 → 24h → 放回），比"到期即回收"温和得多。但**判据仍然只是"沉默"**——没有任何正向证据证明持有者已退出。

### 2.4 命名撞车：`Run`

`agent-runs.js:16` `MAX_RUNS = 50`「内存保留的 run 数（超限丢最老）」，状态 `queued/running/done/failed/aborted`——这是**内存态 LLM 执行轮次**，重启即丢。

👉 与 Orca 的 `Run`（**持久**命名空间 + coordinator inbox）**同名不同义**。

## 4. 对 MemoryOS 的启发清单

### 🔴 P0-1｜`unverifiable` 缺失：reaper 用"沉默"授权回收

**Orca 依据**：
> Only **positive proof of exit** authorizes stop, abandon, or retry; only an **accepted settlement** authorizes release. Every other observation, **absence included**, is a checkpoint.

**MemoryOS 现状**：`daemon.js:704-737` —— 贴条 24h 无人理即 `claim_lock=NULL` + 任务头回 pending。

**风险**：长跑任务（LLM 反思、reembed、批量采集）持锁但超 24h 未心跳时，**写权限被静默剥夺，而进程仍在写** → 新旧持有者并发写同一任务。

**建议**（最小改动、可回滚）：

1. 保留 grace 与贴条（这是共享任务池的现实需要，**不建议照搬 Orca 的"永不回收"**）
2. grace 到期后**只置 `stale` 标记 + 告警**（写 `memory_events` op=`task_lease_stale`），**不再 `claim_lock=NULL`**
3. 回收改为**正向动作**，三选一：新 dispatch 接管（`createDispatch` 自动 supersede 旧的）/ 人工裁决 / **显式** `task_release`
4. 与批次 1 既定的设计口径一致（"到期只标 stale，不回收不释放"）——**批次 1 只落了表和函数，这条规则还没落**

**落点**：`daemon.js` reaper 阶段②；`dashboard-reg-cards.js:1286` 同款分支。

---

### 🔴 P0-2｜Dispatch 权威只接了 2/8 个写入点

**Orca 依据**：
> Lifecycle authority comes from the active Dispatch — not a terminal title, copied ID, **old database row**, provider transcript, or visible pane.

**MemoryOS 现状**：`task_claim` / `task_done` 已接；**未接** 6 处——

| 工具 | 行 | 后果 |
|---|---|---|
| `task_heartbeat` | 552 | 被取代者可继续续命 |
| `task_release` | 594 | 被取代者可释放别人的任务 |
| `task_block` | 647 | 被取代者可阻断任务 |
| `task_reopen` | 686 | 被取代者可重开终态 |
| `task_verify` | 875 | 第三方可绕过 dispatch 收口 |
| `task_supersede` | 927 | 可归档他人任务 |

**建议**：抽一个 `assertDispatchAuthority(db, key, memoryId, agent)` helper（复用批次 1 在 `task_done` 里的四道校验），六处**软模式先接、硬模式可开关**（沿用 `MEMORYOS_A1_ENFORCE` 的软/硬双模范式）。

**落点**：`server-reg-task.js` 六处；helper 可置于 `db.js` 或 `server.js` 共享层。

---

### 🔴 P0-3｜`consumer_fenced` 无主动通道

**Orca 依据**：
> If `check` returns `consumer_fenced`, this process no longer owns its Dispatch: the Attempt was re-attached to another worker or settled without you. Stop, do not send `worker_done` … **`consumer_fenced` is the only way you learn that.**

**MemoryOS 现状**：批次 1 在 `task_done` 会拒绝"你已被 d-xxxx 取代"（`server-reg-task.js:796`）。但 worker **只在尝试写入时**才得知；中间可能已经白干很久。

**建议**：让 `task_heartbeat` 的回执承载 fence 位——**心跳是 worker 天然的轮询点**，零新工具：

```
<state> {"op":"task_heartbeat","id":4197,"fenced":true,"superseded_by":"<hex>","next_action":["task_next"]}
```

**落点**：`server-reg-task.js` `task_heartbeat` 返回体（扩 `stateReceipt` 字段）。

---

### 🟠 P1-1｜存活三态未落地，新索引无人消费

`idx_dispatches_lease`（`db.js:312`）已建，**全仓无任何查询消费它**（grep 零命中）——即 dispatches **没有自己的 stale 判定**，只有 cards 有。

**建议**：daemon 增加 dispatch 侧的 stale 扫描；**只标不回收**（与 P0-1 同一规则，一次改动两处受益）。

---

### 🟠 P1-2｜Task-spec 五要素无结构

**Orca 依据**：Target / Change / Constraints / Ownership / Observable acceptance。

**MemoryOS 现状**：`task_assign`（210）是自由文本 + `depends_on`；`[gate:预设]`（186）只覆盖第 5 项，且做得比 Orca 更硬（**fail-closed 回退 pending**，这点 MemoryOS 更强）。

**建议**：`task_assign` / `task_delegate` 的 zod 增 4 个**可选**字段（target/change/constraints/ownership），渲染进任务头。**先软后硬**——观察使用率再决定是否 fail-closed。

---

### 🟠 P1-3｜完成后"三选一"无强制枚举

**Orca 依据**：
> do not end the coordinator turn until [the reclaimable enumeration] returns none.

**MemoryOS 现状**：`task_release` 存在，但没有"settled 之后必须显式决策"的强制口。

**建议**：`task_next`（969）增加一段「**已结算但待决策的 dispatch**」——复用现成入口，**不新造工具**。这与 MemoryOS 坑 #6「协作死锁」同源。

---

### 🔴 P0-4｜"未知即降级只读"缺失（多 AI 并行的安全阀）

**Orca 依据**：
> If liveness, principal ownership, capability, or the exact legacy contract is unproven, **degrade to read-only inspection** and never fall back to local execution.
> **A retained adoption record alone does not grant mutation authority.**

**MemoryOS 现状**：多 AI 并行时，靠 `CLAIM.md` **人工分区**维持秩序；一旦"谁还在跑、谁已退出、这个文件归谁"无法证明，**没有任何机制强制降级为只读**——仍然允许写入。

**建议**：把"分区"从**文档约定**升级为**可判定的状态**。最小做法：为分区表加 `state = active | unverifiable | released`，未证明 active 的分区在 MCP 写入路径上**降级为只读**（软模式先只告警）。

**落点**：`CLAIM.md` 约定 + 文件写入工具的 ownership 检查。

> ⚠ 这条与 P0-1 是**同一原则的两个落点**（`unverifiable` 在任务侧、在分区侧）。先做哪一侧都行，但**别只做一侧**——否则原则仍是半截。

---

### 🟠 P1-5｜"权威丢失不使产出失效"——这条直接裁决 09-25 未决项

**Orca 依据**：
> Adoption preserves the live agent process, PTY/session, terminal handle, tab/pane, worktree or folder workspace, Task, and Dispatch. It never restarts or replaces the worker and never revives the retired scheduler.
> **Loss of lifecycle authority does not invalidate the existing process, assignment, or filesystem work.**

**对未决项的意义**：09-25 的 `convergeLinkedCards` 一族是"**僵尸会话的在制品**"——按 Orca 口径，**会话死了 ≠ 产出失效**。原协调者失去生命周期权威，**不会**使其文件系统工作失效。

**结论**：选项 **A（先收口）**、**B（hunk 级暂存）** 有据；**选项 C（丢弃）缺少依据**。这一条把未决项从"感觉"变成"有据"。

> 另注：Orca 明文 *never restarts or replaces the worker*——同理，**不该因为原会话失联就另起一个写者去接管同一批文件**（见 P1-6）。

### 🟠 P1-6｜"权威不明时不得另起写者"——与你既有红线同源

**Orca 依据**：
> **Never take over while the original coordinator is actively coordinating.**
> Do not launch a replacement editor merely because Orca updated or **authority is unclear**. **Keep the original worker as the only editor until a stable handoff point**, then use a fresh current Dispatch in a **conflict-free placement**.
> A fresh worker means a fresh agent terminal, **not** a new Git worktree. Use the current or an exact existing workspace by default. Create a worktree only when the user requested one or **a concrete checkout or filesystem conflict makes sharing unsafe**.

**判读**：这三句与用户既有红线**逐条同源**：

| Orca 原文 | 既有红线 |
|---|---|
| authority is unclear → keep the original worker as the only editor | 「旧端口杀不掉就根治，**绝不允许新开端口绕过**」 |
| create a worktree only when a concrete conflict makes sharing unsafe | 「多 AI 并行**先读 CLAIM.md**，确认要改的文件不在他人独占区」 |
| Never take over while the original coordinator is actively coordinating | 「原协调者还在时**绝不接管**」（接手流程第 1 步）|

**结论**：红线的**理论依据**在这里找到了——不是"经验之谈"，而是**编排层的安全底线**。可把这三条引作 `CLAIM.md` 的判据来源，让分区约定从"我们约定"升级为"有据可依"。

### 🟠 P1-7｜takeover 的最小正确形态（供未来"接手"参考）

**Orca 依据**：接管**只做两件事**——**隔离旧协调者** + **把 pending mail 移入当前 Run 投递**；**保留** live workers / Tasks / Dispatches / 进程 / 文件。

**映射**：MemoryOS 的"接手"目前是**人工流程**（读 CLAIM → 评审 plan → 核查已完成 → 只接授权范围 → 登记防复发）。Orca 的三条可直接补进该流程：

1. **接管前置条件**：原持有者不可用 **或** 无法证明保有权（Downtime 判断要留痕，不能凭"它额度用完了"这种推断）
2. **接管边界**：只隔离旧持有者 + 转投递；**不重启、不替换、不复活已废弃的调度器**
3. **收尾**：在 **conflict-free placement** 起新 dispatch（= 登记 CLAIM 分区后再动手）

**落点**：`CLAIM.md` §4 登记模板增"接管前置条件 / 接管边界 / conflict-free 确认"三栏。

### 🟡 P1-8｜at-least-once 与幂等的配套

**Orca 依据**：
- `[LEGACY RECOVERY REPLAY — MAY HAVE BEEN SEEN]` = **一刀有界的 at-least-once 切割重放**，要求 *Process it idempotently*
- 心跳与升级消息在手工重试中**保持 at-least-once**
- *If an ask may already have been answered, run the exact non-consuming recovery check … before creating any new question.* **Never guess among identical question threads.**

**映射**：这正是 P2-1（`request_id` 幂等）的**上位理由**——幂等不是"锦上添花"，而是**切割/重放场景下的必需**。两条应合并实施：先 `request_id`，再谈接管重放。

**MemoryOS 现状**：MCP 写工具无幂等键。agent 网络超时后无法判定"是否已生效"，只能重试 → 重复 done / 重复 release。

## 5. 术语撞车（最容易被忽略的风险）

MemoryOS 自己的坑 #3 就是「**语义漂移**」，而 Orca 对照下**已发现三处同名不同义**：

| 术语 | Orca 义 | MemoryOS 义 | 风险 |
|---|---|---|---|
| **Run** | 持久命名空间 + coordinator inbox | `agent-runs.js` **内存态** LLM 执行轮次（`MAX_RUNS=50`，重启即丢）| 跨 agent 沟通时"Run 是什么"必漂移 |

## 9. 接管与放置（takeover & placement）

> 来源：`references/legacy-contract-migration.md` + `references/placement-and-remote.md`

### 9.1 三种权威标签（按"是否需要变更权"分流）

| 标签 | 性质 | **允许动作** |
|---|---|---|
| `[LEGACY COMPATIBILITY]` | live and attested | 只跑**随消息原样打印**的命令：同一可执行文件、同一参数。*Do not translate from memory, broaden the recipient* |
| `[LEGACY RECOVERY REPLAY — MAY HAVE BEEN SEEN]` | 一刀**有界**的 at-least-once 切割重放 | **幂等**处理；只按显示的指引 ack |
| `[LEGACY READ-ONLY]` | 仅检查 | **无回复、无 ack、无生命周期变更** |

要点：无标签的当前消息走当前 grammar；**现行** Run / Dispatch / 联邦附着**优先于** legacy 回退。且——**仅有一条"收养记录"不授予变更权**。

### 9.2 接管的硬约束

1. **Never take over while the original coordinator is actively coordinating.**
2. 接管 = 只**隔离旧协调者** + **pending mail 移入当前 Run 投递**；**保留** live workers / Tasks / Dispatches / 进程 / 文件
3. *it must not spawn, write, signal, stop, switch, focus, split, or inject a terminal*——恢复只允许**恢复同一个 PTY**，不做任何写/信号/启停

### 9.3 放置原则（对多 AI 并行直接适用）

- 新 worker = 新 **agent 终端**，**不是**新 Git worktree
- **默认共用当前 / 精确已有工作区**；只在"用户明确要求"或"**具体 checkout / 文件系统冲突使共享不安全**"时才隔离
- **执行位置 ≠ 权威位置**：`--on` 只选 worker 的执行服务器，**Run 与 Task 仍在当前服务器权威**（对应：代码跑在哪台机器，不改变任务权威在哪）
- 混版本底线：未知能力**不猜**；连接丢失 / 超时 / 缺清单 → 一律 `unverifiable`，**绝不合成 exit、绝不用客户端本地动作替代**

### 9.4 判读

§9.3 第一条是 `CLAIM.md` 分区表的**理论依据**：**分区不是默认，而是"具体冲突"时的例外**。这修正了一个容易走偏的直觉——多 AI 并行不等于"人人隔离"，而是"**默认共享，冲突才分区**"。

§9.1 的三标签分层也值得借鉴：**把"这个在制品我还要不要动"变成一个显式标签**，而不是靠"我记得它是谁的"来判断。

## 10. AI Vault：Orca 的记忆/检索层（本轮新取证）

> **取证结论**：Orca 的 `skill-guides/`（8 篇）里**没有任何记忆/检索指南**，但 **源码里有完整实现**——它对 22 种 agent 的**本地会话转录**建索引并提供全文检索，内部名 **AI Vault**。上一轮 handoff 的"AI vault search"由此**证实**（见 §11）。

### 10.1 定位：索引的是"转录"，不是"知识"

- **索引对象**：本地文件系统上的 agent 会话转录，覆盖 **22 种 agent**（claude / codebuddy / codex / hermes / pi / omp / prime-agent / cursor / gemini / antigravity / rovo / copilot / opencode / opencode2 / zcode / grok / openclaw / devin / droid / cline / kimi / muse）
- **索引单位**：`AiVaultSession`（`sessionId` / `agent` / `cwd` / `branch` / `model` / `filePath` / `messageCount` / `totalTokens` / `previewMessages` / `resumeCommand` / `subagent`）
- **两种能力分离**：`aiVault.listSessions`（扫描列举，排序 `updated|created`）与 `aiVault.search`（全文检索，排序 `relevance|newest`）；请求侧 `scope: conversation|all`、`freshness: indexed|wait-until-current`

**判读**：Orca 把**原始转录**当第一事实源，索引是可重建派生物（有 `generation` 换代）。MemoryOS 恰恰相反——**结构化条目**才是第一事实源，向量/FTS 是派生物。两者共同的底层纪律是：**派生物可重建 + 派生状态必须可观测**。

### 10.2 响应契约：四态 discriminatedUnion

| kind | 含义 | 关键字段 |
|---|---|---|
| `results` | 正常结果 | `hits`（≤上限）、`page{cursor,hasMore}`、`generation`、`truncated`、`durationMs`、`debug?`、`hosts?` |
| `stale-cursor` | 游标因保留期清理失效 | `generation`、`expectedGeneration?` → **客户端重发第 1 页** |
| `malformed-cursor` | 调用方构造错误 | 走 CLI 错误通道 |
| `unavailable` | 服务不可用 | `reason: disabled / not-ready / no-service / scope-unknown` |

**判读**：把"没有结果""服务不可用""游标失效"拆成三类，**绝不混为一谈**。

### 10.3 索引状态账本（`status`）—— 这才是"持久状态账本"

```text
enabled, phase: idle|indexing|current|degraded|closed,
filesIndexed, filesDue, filesFailed, messagesIndexed?,
degradedRoots[]: { root?, reason },        // root 经中继被隐去，计数保留
lastReconcileAt, lastSweepCompletedAt,
sessionsByAgent?, generation
```

三条纪律：

1. **对账与清扫是两个周期**：`lastReconcileAt`（发现 `filesDue` / `filesFailed`）与 `lastSweepCompletedAt`（清扫）分别记时
2. **代数是防漂移的锚**：`generation` 随索引推进递增，检索回执与游标都按它判失效
3. **降级要指名**：`degradedRoots[]` 精确到"哪个根 + 为什么"；跨中继时根名被隐去，但**计数仍保留**

### 10.4 可直接借的机制

| 机制 | Orca 做法 | 为什么值钱 |
|---|---|---|
| **显式截断契约** | `truncated{candidates, snippets, query, freshness}` 四类各自有文案（"ranking saw only the first batch…"） | "排序只看到第一批候选"是**召回不足的自我暴露**；不暴露就无法归因 |
| **游标 + stale-cursor** | 索引一动，旧游标作废并**明说**，客户端重发第 1 页 | 分页的幂等解，避免翻页错位 |
| **证据分离** | `hit.evidence{snippet, role, timestamp}` 可为 null；无证据时**显式输出** `no text evidence for this match` | **无证据 ≠ 没找到**；且给 snippet 而非全文，控制回执体积 |
| **源存在性三态** | `source.presence: present / unverifiable / missing`；zod `refine` 强制 `Only present sources may have a resume command` | **与 §1.4 存活三态同源**——"未知即降级"在检索层复用 |

配套三条：

- **查询计划可观测**：`plannerReport{route: phrase|and|or|typo+*, repairedTerms[], scope}` + `debug` → "为什么召回这些"可解释
- **部分失败可见**：`hosts[].outcome` 七态（`searched / stale / disabled / not-ready / no-service / unreachable / scope-unknown`），跨机合并时**每台单独报结局**而非整体失败
- **零内容会话不隐藏**：`isAiVaultSessionRecoverableEmpty` 把"零轮但仍有可恢复信号（`queuedMessageCount` / `subagentTranscriptCount`）"显式区分 —— 与 §1「权威丢失不使产出失效」同源

### 10.5 与 MemoryOS 对标（MemoryOS 侧均为逐行实证）

| 维度 | Orca AI Vault | MemoryOS 现状 | 判定 |
|---|---|---|---|
| 检索融合 | planner 路由（phrase/and/or/typo）+ 修复词 | `search.js:4` `RRF_K=60`；语义+词法 RRF 融合 + 意图聚焦度动态加权（`search.js:178`）| **MemoryOS 不弱**，只是不对调用方暴露 route/repairedTerms |
| 索引侧健康 | `status` 含 `phase` / `filesIndexed` / `filesDue` / `filesFailed` / `lastReconcileAt` / `lastSweepCompletedAt` / `generation` | `memory_health`（`server-reg-memory.js:752`）只测**使用侧**（search/write/returned/cited、触发率、空召回率、写读比）| **缺口** → P1-9 |

| 降级可见 | `unavailable.reason` 四值 | `semanticDegradation()` 全局标记 + `degNote`（`search.js:34`）| **已达标**（口径略粗）|
| 命中回血 | 索引侧 `updatedAt` | 命中即升 `hit_count` + `last_seen_at`（`search.js:247-255`）| MemoryOS 反而更细 |
| 跨主机 | `executionHostId` + `hosts[]` 七态 | 无（单机）| 不需要（YAGNI）|

### 10.6 由本章新增的启发（P1-9 ~ P1-12）

- **P1-9（建议优先）｜`memory_health` 增"索引侧"段**：现有 health 只回答"有没有在用"，不回答"索引是否完整"。建议补：向量覆盖率（有 `vec` / 总 active）、待重嵌数（`embed-backfill.js` 已有能力）、上次重建时间、索引代数。**零新表，纯读**。
- **P1-10｜检索分页（cursor）**：`limit` ≤ 50 无翻页，"200 条相关只看得到 50 条"当前不可见。可后置。
- **P1-11｜截断契约补三类**：候选集被截（`candidates`）、snippet 被缩（`snippets`）、查询被切（`query`）。`degNote` 已证明"显式告知"的价值，扩面即可。
- **P1-12｜证据与来源存在性分离**：长文本/多来源场景，回执应能回答"这条来自哪一轮、谁说的"。注意 MemoryOS 是"条目即事实源"、无转录层，**此条须按自己语义裁剪，不宜照搬**。
