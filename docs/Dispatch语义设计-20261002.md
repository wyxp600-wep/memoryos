## 0. 一句话定位

Orca 的编排层明确规定了权威的来源与排除项：

> Lifecycle authority comes from the active Dispatch — **not a terminal title, copied ID, old database row, provider transcript, or visible pane.**

MemoryOS 目前**没有"尝试（attempt）"这个实体**。"谁有权改这个任务"被拆散在四个载体上，各自为政、且**都可以被绕开**。

**Dispatch 的价值 = 把这四处收成一个可查询、可换代、可取代、可审计的实体。**

## 1. 问题：权威散落在四处

| 载体 | 位置 | 表达的能力 | 缺口 |
|---|---|---|---|
| `memories.version` | `db.js`（行级乐观版本）| 并发写冲突（CAS）| 每次任何改写都 +1，**表达不了"第几次尝试"** |
| `cards.claim_lock` | `db.js:227` | 租约互斥 | **随机 hex，不携带身份**，查不出持有者 |
| `session_id` | 仅落事件 payload | 审计线索 | **无实体**，无法查询"当前谁持有" |
| 任务头 `[assignee:]` | 文本 | 归属 | 可被任意改写（历史脏值 54%）|

**直接证据（权威可被省略）**——`server-reg-task.js:385`：

```js
if (args.lease_token && claimLocks.length && claimMismatch)
```

**不传 `lease_token` 就跳过 fencing 校验**。即调用方可以通过"省略参数"绕开租约互斥，这与 Orca 的要求（"never reconstruct, translate, or broaden those arguments"）正交违背。

## 3. 数据模型

```sql
CREATE TABLE IF NOT EXISTS dispatches (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  dispatch_key     TEXT    NOT NULL UNIQUE,           -- 对外句柄 d-<12hex>，取代裸 lease_token
  memory_id        INTEGER NOT NULL,                  -- 关联任务
  agent            TEXT    NOT NULL,                  -- 持有者（AGENT_NAME_RE 口径）
  session_id       TEXT,                              -- 会话隔离（原问题 #7）
  credential_id    INTEGER,                           -- A1 凭据追溯
  state            TEXT    NOT NULL DEFAULT 'active', -- active/settled/released/superseded/stale
  generation       INTEGER NOT NULL DEFAULT 1,        -- 换代计数（接管时 +1，fencing 核心）
  outcome          TEXT,                              -- succeeded/failed（结算必填，Orca 口径）
  evidence         TEXT,                              -- 结构化终态 JSON（回执）
  lease_expires_at TEXT    NOT NULL,
  heartbeat_at     TEXT,
  started_at       TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  settled_at       TEXT,
  superseded_by    INTEGER                            -- 被哪次 dispatch 取代
);

-- ★ 机器保证「一个任务同时只有一个 active 尝试」——不靠 agent 自觉
CREATE UNIQUE INDEX IF NOT EXISTS idx_dispatches_active
  ON dispatches(memory_id) WHERE state='active';
CREATE INDEX IF NOT EXISTS idx_dispatches_agent ON dispatches(agent, state);
CREATE INDEX IF NOT EXISTS idx_dispatches_lease
  ON dispatches(lease_expires_at) WHERE state='active';
```

`idx_dispatches_active` 的写法与既有 `idx_resource_locks_active`（`db.js:352`）**逐字同构**，无新范式引入。

### 3.1 与 `memories.version` 的分工（避免"两套版本"混乱）

| | 管什么 | 何时变化 |
|---|---|---|
| `memories.version` | **并发写冲突**（现有 CAS）| 任何改写都 +1 |
| `dispatches.generation` | **尝试的世代**（谁能写）| 仅在接管 / 换代时 +1 |

两者**互补而非替代**。现有 CAS 事务与 72 个 export 签名**一行不改**。

## 4. 权威规则

**写权限的唯一定义**：调用方必须持有该任务的 `active` dispatch，且 `agent` 匹配。

新校验函数 `assertDispatchAuthority`：

```
1. dispatch_key 可解析 → dispatch.state === 'active'
2. dispatch.memory_id === 目标任务 id
3. dispatch.agent === 调用方（或 credential.scope === 'admin'）
```

**落地后的语义**：

- 并发接管 = **同一事务内**「旧 dispatch 置 `superseded` + 插新 dispatch + `generation + 1`」
- 被取代的旧持有者再写入 → 命中 `superseded` → **拒绝**，回执告知"你已被 d-xxxx 取代"
- **任务头 / 卡片 / DB 行都不能单独授权写**（现状 `assertTaskAlive` 只看列、`readTaskState` 只看头）

## 5. 存活三态（原问题 #13 的正解）

Orca 的固定词汇与安全底线：

> Liveness is layered … A live terminal can still hold a dead or stuck agent.
> Only **positive proof of exit** authorizes stop, abandon, or retry; only an **accepted settlement** authorizes release. **Every other observation, absence included, is a checkpoint.**

MemoryOS 现状是**租约到期即回收**。改为：

| 态 | 判据 | 允许动作 | **禁止动作** |
|---|---|---|---|
| `live` | active 且未过期且心跳新鲜 | done / heartbeat / release | — |
| `unverifiable` | active 但**心跳超时**（未到期）| 心跳唤醒、被接管 | **回收、判失败** |
| `exited` | 显式 done/release，或到期 + **正向证据** | 结算、复用、释放 | — |

**关键行为变化**：租约到期**只标记 `stale`，不回收、不释放**。回收必须有**正向动作**（新 dispatch 接管 / 人工裁决 / 显式 release）。

这根治 #13 的真实危害——**长任务超时被误判为"没人做"，而进程仍在写**。

## 6. 兼容与迁移

沿用仓库既有的**软 / 硬双模式**范式（`MEMORYOS_A1_ENFORCE` 先例）：

| 模式 | 行为 |
|---|---|
| 默认（软） | 不传 `dispatch_key` → 走现状逻辑 + 事件留痕 `legacy: true` |
| `MEMORYOS_DISPATCH_ENFORCE=1`（硬）| 必须携带 `dispatch_key`，缺失即**拒绝**（fail-closed）|

**迁移**：本仓库无 `PRAGMA user_version`，新表走**建表即存在**（`CREATE TABLE IF NOT EXISTS`），存量任务在**首次被认领时**自然生成 dispatch，无需一次性回填。

**不删** `cards.claim_lock`：改为**写 `dispatch_key` 作投影**（保持"cards 只做投影"的既有语义），卡片侧零权威。

## 10. 权衡与选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 新增 `dispatches` 表** | 唯一权威锚点，一表覆盖 #2/#7/#13；有 `resource_locks` 先例，零新范式 | 新表 + 6 工具改造 + 迁移 | **推荐** |
| B. 复用 `resource_locks` | 零新表，`fencing_token` 现成 | 其语义是"资源锁"（文件/端口/DB），混入任务主权会纠缠；缺 `outcome`/`evidence`/`generation` | 不推荐（该表继续管文件/端口）|
| C. 只强化 `lease_token` 编码 | 零 DDL | 字符串**无法查询**"当前谁持有"，无法记 outcome/evidence，审计仍靠事件流反推 | 不推荐——让 token 承担它承担不了的职责 |
| D. dispatch 做成 cards 的一行 | 复用卡片 | cards 是投影层（自身文档明示"cards 只做投影"），让投影承担权威 = 再造双源 | 与自身架构矛盾 |

**推荐 A**。核心理由：以**最小的新范式**（照抄既有 partial unique index）换取唯一权威锚点，且**不动**现有 CAS 事务与 export 签名。
