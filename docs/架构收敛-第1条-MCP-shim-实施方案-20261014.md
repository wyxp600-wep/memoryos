## 0. 一句话

把散在 N 个 MCP 进程里的 DB 连接、嵌入模型、进程内缓存、门禁收敛到 **dashboard（核心）** 一个进程；
`server.js` 退化成只做 stdio → HTTP 转发的薄壳。**默认走原路径（direct），shim 是显式开关。**

## 1. 现状证据（实测，非推断）

### 1.1 进程与内存（同一时刻快照）

| 进程 | 私有内存 | 说明 |
|---|---|---|
| dashboard.js | 1192.4 MB | 持有模型 + DB + 全部进程内缓存 |
| server.js #1 | 895.8 MB | MCP，已自载一份 BGE-M3 |
| server.js #2 | 796.3 MB | MCP，已自载一份 BGE-M3 |
| server.js #3 | 119.2 MB | MCP，未触发过语义检索（懒加载未爆） |
| server.js #4 | 114.0 MB | 同上 |
| daemon.js | 107.5 MB | 走 api 模式，不驻留模型 |

结论：**模型驻留份数 = Agent 数 + 1**，且问题是**延迟暴露**的。

### 1.2 跨进程缓存失效通道

- 全仓 `grep data_version`：**零命中**。
- 向量缓存版本 = 进程内计数器（`db.js`：`vecState(db).version++`），TTL 兜底 **60s**。
- L1 结果缓存 TTL **30s**，失效键 = `vectorCacheVersion(db)`（同一进程内计数器）⇒ 跨进程写 **L1 也看不见**。

### 1.3 工具面（口径：`node dist/server.js --list-tools`）

- 执行面关闭：**29** 个（memory 13 + obsidian 3 + task 12 + tool_guide 1）
- `MEMORYOS_EXEC_ON=1`：**32** 个。文档所述 26 / 27 均**已过期**。

## 2. 与 Claude 方案的差异

### 2.1 四处修正（均已实证）

| # | Claude 原设想 | 实证结果 | 本方案改为 |
|---|---|---|---|
| 1 | 开关写 `data/settings.json` | 核心落盘配置是 **`data/config.json`**（`configFilePath()`，已有 `readDiskConfig`/`writeDiskConfig`） | 写 `config.json`，复用既有通道；**shim 读该文件须容忍半写状态**（解析失败按 direct 处理），**dashboard 写用临时文件 + rename** |
| 2 | 「`server.js` 只加几行，注册代码一行不改」即可让核心响应 `/ops/:tool` | 注册编排在**模块顶层**（非函数）；`fastmcp` 工具体是**私有字段 `#tools`**，实例外取不到 | **必须**新增 `server-tools.js`：抽 `registerAllTools(server, ctx, opts)` 并**额外产出 `Map<name, def>`** |
| 3 | 跨进程失效靠 `PRAGMA data_version` 轮询 | 方向对但**会 thrash**——见 §2.2 | 改为**向量相关计数行**（本文件 §4-1c） |
| 4 | 26 个工具全部转发 | 实测 **29 / 32**，执行面 3 个是 env 条件暴露 | 转发面以**核心 `/ops/catalog`** 的启用位为准；schema 取本地同一份注册 |

### 2.2 实测：`PRAGMA data_version` 的语义（决定了 1c 的改法）

探针（两条连接 A/B 同一库，Node `node:sqlite`）输出：

```
初始      A= 2   B= 2
A 自写后  A= 2   B= 3    A变化: false  B变化: true
B 写后    A= 3   B= 3    A变化: true   B变化: false
B 再写后  A= 4            A变化: true
A 自写后  A= 4            A变化: false
```

两条结论：

1. **同连接自己的写不改变自己看到的 data_version** ⇒ 核心自身搜索产生的 `hit_count` / `usage` 回血**不会**打掉自己的缓存（这点是安全的）。
2. **其他连接的任何提交都会改变** —— 包括迁移期仍在 direct 模式的 MCP 进程搜索时写的 `hit_count` 回血。这些写**与向量池无关**，却会把核心的向量缓存和 L1 全量打掉 ⇒ **比现状的 60s TTL 更差**。

⇒ 不能拿 data_version 当失效信号。1c 改用「只在向量相关写发生时递增的计数行」。

## 3. 目标结构

```
现状:  Agent×N → server.js×N ─┐
       daemon ──────────────────┼→ memory.db   （各自 DB 连接、各自缓存、各自模型）
       CLI / dashboard ─────────┘

目标:  Agent×N → shim×N ──┐
       daemon / CLI ───────┼→ 核心(dashboard) → memory.db
                           ┘   （单一 DB、单一模型、单一缓存、单一门禁）
```

#### 4-1b 前置①：调用方身份透传（Claude 二轮评审新增，**1b 必须做**）

问题：现在身份是**进程级常量** —— `server.js` 启动时读 `MEMORY_AGENT` / `MEMORY_AGENT_FPATH` 注入 ctx，注册时被 `const { AGENT, AGENT_FPATH } = ctx` **冻结**（`server-reg-memory.js:18`）。工具挪到核心执行后，随请求到达的是**不同 Agent**，若仍用进程常量 ⇒ 所有写入都记在 dashboard 名下，归属 / 审计 / A1 门禁全部失真。

实测改造面（`grep AGENT` 计数）：

| 文件 | 命中数 |
|---|---|
| `dist/server-reg-task.js` | 60 |
| `dist/server-reg-memory.js` | 36 |
| `dist/server.js` | 17 |
| `dist/server-reg-obsidian.js` | 6 |
| **合计** | **119** |

设计：

- `server-tools.js` 导出身份访问器 `agentName()` / `agentFpath()`：**核心侧**从 `AsyncLocalStorage` 取当前请求身份；**direct 模式**回落到进程 env 常量（**行为与改前逐字一致**）。用 ALS 而非模块级可变量，因为 handler 内部有 await（嵌入 / LLM 调用），会并发交错。
- 三个 reg 文件把 `AGENT` / `AGENT_FPATH` 标识符 **机械替换**为访问器调用（`AGENT` → `agentName()`）。加一条静态守卫：替换后三个文件内不得再出现裸 `AGENT` 标识符（防漏改导致静默错记）。
- 核心 `/ops/:tool`：每请求 `als.run({ agent, agentFpath, credential }, () => def.execute(args))`，身份来源 = shim 透传的请求头 / body 字段；**逐请求校验**（含 A1 凭据，沿用既有 `isCredentialValid` 语义，具体形态 1b 开工前先读 A1 实现再定稿）。
- 验收：**两个不同 `MEMORY_AGENT` 的 shim 各写一条，`memories.agent` 各自正确**（§5 ⑧）。

#### 4-1b 前置②：长耗时与取消语义（Claude 二轮评审新增，**1b 必须做**）

问题：`exec_run` / `task_verify` 的验收子进程改在核心里跑；MCP 客户端取消或断开后，核心若不知道，会留**孤儿进程**。

实测已有底座：`exec-tools.js` 已有 `killTree()`（Windows `taskkill /T /F`）与 `timeout_ms`（默认 30000、上限 600000）——**只缺外部取消信号**。

设计：

- shim 侧：**按工具设超时**（长耗时工具用其自身的 `timeout_ms` 语义，其余用短超时）；客户端取消 / stdio 关闭 → `AbortController.abort()` 中止该 HTTP 请求。
- 核心侧：`/ops/:tool` 监听请求中断（`req.raw` 的 close/aborted）→ 生成 per-request `AbortSignal` → 注入 handler（`exec_run` / `task_verify` 把 signal 接到 `killTree`）。
- 1b 开工前核实：`fastmcp` 是否把 MCP 的 `notifications/cancelled` 透传为 execute 的 signal（若无，则由 shim 自行在传输层判定取消）。
- 验收：取消后**无孤儿子进程**（§5 ⑨）。

#### 4-1b 前置③：`/ops` 返回口径核对（1a 遗留项）

1a 的 `/ops/:tool` 对**裸值返回**做了归一（补 `content` 包装），理由是该类工具 `def.execute` 返回裸字符串（如 `memory_projects`），直接给 shim 会拿不到 MCP 形结果。这与 fastmcp 协议层自己的包装**是否逐字节等价**尚未验证（1a 只验了"结构正常"，没做客户端可见输出的逐字节比对）。

⇒ 1b 必须补一条实测：**同一工具、同一参数，分别经「客户端 → 直连 server.js」与「客户端 → shim → 核心」两条路，比对客户端实际收到的内容逐字节一致**（含 MCP 形 / 裸值两类工具各抽一个）。若发现不等价，改 `/ops/:tool` 为**回裸值 + 由 shim 侧 fastmcp 包装**（更贴近"同一份注册、同一层包装"）。

### 阶段 1c：跨进程失效（**设计已按 §2.2 修正**）

| 文件 | 动作 | 内容 |
|---|---|---|
| `dist/db.js` | 改 | 新增**向量相关计数行**：`memories` 的插入 / 改写 / 状态流转 / 合并 / 删除 / 向量回填等**会改变候选池**的写事务里，顺手递增 `config` 中的单行计数（`vec_gen`）。核心在检索入口读该单行（O(1)）并与上次值比对，变化即 `vecState(db).version++`（**一处 bump 同时失效向量缓存与 L1**） |
| `dist/db.js` | 改 | **`search.js:bumpHits`（`hit_count` / `last_seen_at` 回血）不递增该计数**——它是遥测写，不改变候选池（这正是 §2.2 里 thrash 的来源） |
| 埋点 | 改（**落地口径与计划不同，已更正**） | 计划写 `daemon_log`；**实际**做成进程内统计 `vecInvalidationStats()`（`total`/`lastAt`/`byHour`/`bySource`），并经 `GET /ops/catalog?vec=1` 暴露（门控以保住无参 GET 快照）—— 理由是本次**未新增路由**、也未改动 `daemon.js` 的定时任务 |
| 冒烟 | A 分区 | 断言「每一次向量相关写都递增了计数行」：跑一遍已知写序列，比对计数增量 vs 廉价的 `COUNT(*)+MAX(id)+SUM(version)` 探针（**兜底自证**，防漏改点） |

不在本阶段：`/ops/invalidate`（不需要）、`search.js` 改动（不需要）。**60s TTL 保留为兜底**——漏改某个写点也只是退化到现状，不会永久陈旧。

**① 口径修订（100MB → 150MB）的权衡**：shim 的内存大头约 **110MB**（裸 node 仅 18.6MB），来自**本地工具注册带来的模块图**（fastmcp + zod + db/search/report/ann/embed）。
- 路 A（采用）：保留本地同一份注册 ⇒ schema / 描述 / 风险前缀与 direct **逐字节一致**，无漂移风险；代价是基线 ~129MB。
- 路 B（未采用）：改从核心 `/ops/catalog` 拉 schema 再重建 ⇒ 可省掉 db/search/report 等模块图（基线有望降到 ~60–80MB），但要把 JSON Schema **反向重建为 fastmcp 需要的 zod 对象**，且 schema 一旦不同步就会**静默漂移**（正是"客户端看到与被执行的不一致"这类难查问题）。
- 因此把阈值放宽到 **150MB**；真正要守的三条不变：**零 DB、零模型、不随检索增长**（实测均成立）。
