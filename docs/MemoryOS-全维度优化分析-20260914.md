## 1. 安全性

### 1.1 【严重】热更新链路：清单路径穿越 + 无签名校验

- **问题描述**：`services/updater.js` 直接使用远端清单字段拼路径，且只做哈希比对：
  - `const local = path.join(getKernel(), f.path)` — `f.path` 未规范化，含 `..` 即可越出内核目录；
  - `const target = path.join(tmp, ...f.rel.split("/"))` — 同样无越界断言；
  - `if (sha256Buf(buf) !== f.hash)` — 哈希与清单**同源**（都来自 `updateUrl`），不构成信任链。
- **影响范围**：`updateUrl` 被劫持 / DNS 污染 / 中间人 → 可向内核目录**之外**任意路径写文件（Windows 下可覆盖用户目录、启动项），随后 `restartCore()` 以用户权限拉起被替换的 `dashboard.js`。触发路径：托盘「检查更新」与每 30 分钟的 `updater.auto()`。
- **改进建议**：
  1. `path.resolve` 后断言结果必须位于 `getKernel()` / 临时目录前缀内，且拒绝含 `..`、绝对路径、盘符、UNC 的 `rel`；
  2. 清单引入**签名**（Ed25519，公钥内置于壳层）或至少强制 https + 域名白名单；
  3. 落地前把旧文件 sha256 清单写入 `backup/hotupdate-*/manifest.sha256`，供回滚审计。
- **验收**：构造 `f.path="../../evil.txt"` 的清单 → 更新被拒绝且不产生越界文件；正常清单仍可更新。

### 1.2 【严重】`obsidian_write_note` 的 `folder` 参数路径穿越

- **问题描述**：`dist/obsidian-sync.js` 中 `writeNoteToVault()`：
  ```js
  const safeTitle = opts.title.replace(/[\\/:*?"<>|#]+/g, "_")...   // title 已清洗
  const dir = path.join(vaultRoot, folder);                          // folder 未清洗
  fs.mkdirSync(dir, { recursive: true });
  fs.writeFileSync(filePath, ...);
  ```
  `folder` 来自 MCP 工具入参（`server.js` 的 `obsidian_write_note`）与 HTTP 路由，未做 `..` / 绝对路径校验。
- **影响范围**：任意 MCP 客户端或同机 HTTP 调用方可将 `.md` 写到 vault 之外任意可写目录（内容可控 → 等价任意文件写）。属"受限模式"未覆盖的旁路。
- **改进建议**：对 `folder` 复用 `title` 的清洗思路（禁 `..`、绝对路径、盘符、UNC），并对最终 `filePath` 做 `vaultRoot` 前缀断言；`server.js` 侧用 zod 收紧为「单层相对目录名」。
- **验收**：`folder="../../pwn"` → 报错拒绝；`folder="子目录"` → 正常写入。

### 1.3 【高】敏感凭据落盘与传输加固不足

- **问题描述**（四处，逐条实证）：
  1. `dist/dashboard.js:236-241` 把 `cfg.llmKey`（LLM API Key）写入 `config.json`，`writeDiskConfig()` **未收紧文件权限**；`services/core-process.js:55` 再经环境变量 `INGEST_KEY` 传给子进程。（当前实测 `%APPDATA%\MemoryOS\config.json` 仅 58 字节、未含 key，属**代码路径风险**而非既成泄露）
  2. `security/token.js` 写 `data/token` **未指定 mode**；同目录的 dashboard 侧自举分支却用了 `mode: 0o600`（不一致）。
  3. `dist/dashboard.js:110` 令牌比较用 `===`（非常量时间）。
  4. `window/main-window.js` 以 `?token=` 形式 `loadURL`，令牌留在窗口 URL 中。
- **影响范围**：同机其它进程/用户/备份链可读凭据；URL 令牌可经日志、截图、浏览器扩展泄漏。与用户既有安全约定（严格保护 API Key / Token）直接冲突。
- **改进建议**：① `llmKey` 走 Electron `safeStorage`(DPAPI) 加密存储，或改为仅内存/仅 env 不落盘；② `data/token` 统一 `0o600` 并同样用 `safeStorage` 包装（`security/token.js` 注释里已自认此属未完成的 P0 路线图）；③ 比较改 `crypto.timingSafeEqual`；④ 前端首访种 cookie 后 `history.replaceState` 抹掉 `?token=`。
- **验收**：`config.json` 中不含明文 key；token 文件权限收紧；错误令牌的 401 响应时间与正确令牌无显著差异。

### 1.4 【中】CSP 拦截内联事件 → 3 处 UI 功能失效

- **问题描述**：`dashboard.js` 下发 `Content-Security-Policy: script-src 'self'`（无 `unsafe-inline`），但页面存在内联事件处理器：
  - `memoryos-dashboard-redesign/index.html:3766` → `<button class="error-reload" onclick="location.reload()">重新加载</button>`
  - `app.js:1713` → 审计日志中的记忆跳转 `<a href="#all" onclick="setTimeout(...)">`
  - `app.js:3047` → 代码块「复制」按钮 `onclick="...navigator.clipboard.writeText(...)"`
- **影响范围**：内核未就绪时的「重新加载」按钮、记忆详情代码块「复制」、审计日志记忆跳转**点击无效**（浏览器拒绝执行内联 handler，控制台报 CSP 违规）。属"安全策略与实现不一致"导致的用户可见功能缺失。
- **改进建议**：改为 `data-*` 属性 + 统一 `addEventListener` 事件委托，彻底移除内联 handler；并把这三处行为写入 `smoke-dashboard` 断言，防止再次回归。
- **验收**：三处按钮点击后行为生效，控制台无 CSP 违规报错。

## 2. 性能瓶颈

### 2.1 【高】主库 72% 页为空闲页，从未回收

- **实证读数**（`pragma page_count` / `pragma freelist_count`，只读连接）：
  ```
  page_size=4096  page_count=13580（55.6MB）  freelist_count=9818  auto_vacuum=0
  → 空闲 40,214,528 字节（72.3%）
  ```
  对照 `data/memory.db.pre-perfopt3-*`（VACUUM 后）仅 15MB —— 即真实数据约 15MB，主库却占 55.6MB。
- **问题描述**：daemon 每日只做 `VACUUM INTO` **备份**，从不回收主库；`auto_vacuum=0`，删除（`merged` 282 / `rejected` 97 条、gram 表重建等）产生的空闲页永久滞留。
- **影响范围**：页缓存/`mmap` 有效命中率下降；全表扫与 `VACUUM INTO` 备份成本约 3.6 倍；SSD 与热更新分发体积。
- **改进建议**：① 先 `VACUUM INTO` 备份，再一次性 `VACUUM`；② daemon 增加「空闲页比 >30% 且非高峰」触发的 VACUUM 治理项（幂等 + `config` 标记）；③ 评估 `auto_vacuum=INCREMENTAL` + 定期 `incremental_vacuum` 的折中（注意模式变更需一次 VACUUM 才生效）。
- **验收**：VACUUM 后 `freelist/page_count < 10%`、`integrity_check=ok`、行数仍为 905；治理项在 scratch 库 `--once` 跑通。

### 2.2 【中 / 验证缺口】ANALYZE 实际从未在真实库生效

- **问题描述**：`MemoryOS-架构与性能分析.md` 附一称「每日一次 ANALYZE（config 标记 `maintenance.analyze_ts` 幂等）」已落地并 ✅ 已验证。实测真实库：
  ```
  sqlite_stat1 存在？ → 0 条（不存在）
  config 表 → 仅 migration.vectors_split_v1 / migration.sectors_v1 / type.deprecated
  ```
  → 该路径**从未在真实库执行**，此前验证仅在 scratch 库 `--once` 完成。
- **影响范围**：查询规划器缺统计信息，索引选择继续依赖手工 `EXPLAIN`；库增长后执行计划漂移风险（该报告 §2.3 自己列为"待办"）。
- **改进建议**：① 真实库手动触发一次 `ANALYZE` 并确认 `sqlite_stat1` 生成；② 补齐「首次运行即 ANALYZE」逻辑（当前仅依赖每日 tick，若 daemon 未长跑则不触发）；③ 把「ANALYZE 时间戳 + stat1 行数」纳入 `/api/health` 输出，使"已落地"可被机读验证。
- **验收**：`sqlite_stat1` 存在且行数 > 0；`config` 出现 `maintenance.analyze_ts`；health 可见。

### 2.3 【中】静态资源零缓存 + 每请求同步全量读盘

- **问题描述**：`dist/dashboard.js:1158-1160`
  ```js
  app.get("/", ...fs.readFileSync(path.join(UI_DIR, "index.html"), "utf8"))      // 172KB + Cache-Control: no-store
  app.get("/app.js", ...fs.readFileSync(path.join(UI_DIR, "app.js"), "utf8"))    // 272KB + Cache-Control: no-store
  app.get("/echarts.min.js", ...fs.readFileSync(...))                            // 1.0MB，无缓存头
  ```
- **影响范围**：合计约 1.45MB 静态资源，每次刷新/切页**重复全量传输 + 重复同步读盘**（阻塞单线程事件循环）；与 `/api/*` 已实现的 ETag/304 优化形成明显不一致。
- **改进建议**：① 启动时一次性读入内存（或按 `mtime` 失效）；② 加 `ETag`/`Last-Modified` + 304；③ `index.html`/`app.js` 用 `no-cache`（协商）替代 `no-store`；`echarts.min.js` 加长缓存 + `immutable`。
- **验收**：二次请求返回 304 且 body 为空；静态路由不再每请求 `readFileSync`（可用计数断言）。

## 5. 架构设计

### 5.1 【中】内核进程无自愈，调度锁无超时

- **问题描述**（三处）：
  1. `services/core-process.js` 子进程 `exit` 仅 `dialog.showMessageBox` 提示，**不自动重启**；`coreChildren` 不清理已退出项，`restartCore()` 会对 stale pid 调 `taskkill`。
  2. `services/scheduler.js` 用布尔锁 `__syncing` / `__ingesting` 防重入，**无超时**；若子进程 hang（ONNX 加载 / 网络），锁永久为 `true` → 调度**静默停摆**。同时 `out += String(d)` 累积 stdout 无上限。
  3. `dist/*.js` 内**无** `process.on('uncaughtException'/'unhandledRejection')`，`dashboard.js` **无** `setErrorHandler`（`grep` 全无命中）。
- **影响范围**：`daemon.js` 挂死 → 治理/备份/检查点/衰减静默停止（无人感知）；`dashboard.js` 崩溃 → 桌面白屏需人工重启。与"托盘常驻、无人值守"的产品定位冲突。
- **改进建议**：① 内核退出按指数退避自动重启（限次 + 熔断），并清理 `coreChildren`；② 布尔锁加超时（超时 kill 子进程并释放）；③ 内核加全局异常兜底 + Fastify `setErrorHandler`（结构化错误体，不泄漏路径）。
- **验收**：手动 kill 内核进程后 30s 内自动恢复可访问；伪造 hang 子进程验证锁在超时后释放。

### 5.2 【中】输入校验不统一：`limit` 无上限

- **问题描述**：同一文件内规则不一致：
  ```
  dashboard.js:326  /api/top          → Number(req.query.limit)          // 无 clamp
  dashboard.js:331  /api/cross-tool   → Number(req.query.limit)          // 无 clamp
  dashboard.js:460  /api/rules        → Number(req.query.limit ?? 500)   // 无 clamp
  dashboard.js:484  /api/tasks        → Math.min(Math.max(...,1),500)    // 有 clamp
  dashboard.js:819  /api/all          → Math.min(Math.max(...,1),2000)   // 有 clamp
  ```
  `limit=1e9`、`abc`（NaN）、`?limit=1&limit=2`（数组）均可直达 SQL `LIMIT`。
- **影响范围**：单请求可触发全表扫 / 超大结果集；叠加 `node:sqlite` 同步阻塞 + 单线程事件循环 → 本机 DoS（低门槛，仅需持令牌）。
- **改进建议**：抽 `clampLimit(raw, def, max)` 助手全量替换；并统一给 GET 路由加 Fastify `schema`（querystring/params/body）做类型与范围校验，替代散落的手工 `Number()`。
- **验收**：三个路由传 `limit=1e9` / `abc` / 数组均返回 400 或按上限截断；`grep` 确认无裸 `Number(req.query.limit)`。

### 5.3 【中】可观测性缺失

- **问题描述**：无慢查询日志、无请求耗时直方图、无错误率统计；可观测手段仅 `console.log` 文本（`skill-sync.js` 21 处、`merge-db.js` 20 处、`daemon.js` 18 处、`obsidian-sync.js` 16 处）与 `daemon_log` 表（3740 行）。
- **影响范围**：性能退化只能靠用户感知——历史上 B 系列瓶颈全部靠**人工 EXPLAIN / 实测**发现，不可持续。
- **改进建议**：① 包一层 `db.prepare` 计时采样（>50ms 记入内存环形缓冲 + 落 `daemon_log`）；② `/api/health` 暴露 p50/p95 请求耗时、慢查询 Top10、`busy_timeout` 重试次数；③ 日志统一 level 前缀，收敛散落的 `console`。
- **验收**：`/api/health` 返回慢查询 Top 与耗时分位；注入一条慢查询可在其中观察到。
