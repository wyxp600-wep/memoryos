# MemoryOS 改造计划（基于 Orca 对标）

> **日期**：2026-10-02
> **性质**：**计划文档，未修改任何代码**
> **依据**：《Orca 多智能体协作机制分析-20261002.md》（§3 逐机制对标 / §4 启发清单 / §10.6 AI Vault 新增项）
> **执行纪律**：四步法 → 最全+最优改动（范围由需求定、深度做满） → 先副本后回写 → 每批过门禁 → 实证后声明

---

## 0. 一句话结论

MemoryOS **不缺协作词汇表**（12 个 `task_*` 工具已覆盖 gate / delegate / verify / supersede / heartbeat / release / block / reopen / next），缺两样东西：

1. **权威锚点的全量接线**——Dispatch 语义已落地，但只接上了写入点里的 2 个
2. **"缺席不授权"的底线**——守护进程仍在用"沉默"授权回收；索引侧健康不可观测

因此本改造的性质是 **接线 + 补可观测面**：**不新建子系统、不引入新框架、不改动现有语义**。

### 批次 C1｜`memory_health` 增"索引侧"段（低风险，零新表）

> 依据 §10.6 P1-9

- 落点：`server-reg-memory.js:752`（`memory_health`）
- 现状：只报**使用侧**（search/write/returned/cited、检索触发率、空召回率、写读比、per-agent 漏斗），**不回答"索引是否完整"**
- 新增（纯读）：向量覆盖率（有 `vec` / active 总数）、待重嵌数（`embed-backfill` 已有能力）、上次重建时间、索引代数

- **影响面**：只读，不改 schema → `/api/health` 哈希**不变**

### 批次 A1｜六处写入点接 dispatch 权威（低风险，**软模式**）

> 依据 §4 P0-2

- 未接的六处：`task_heartbeat`(`:552`) / `task_release`(`:594`) / `task_block`(`:647`) / `task_reopen`(`:686`) / `task_verify`(`:875`) / `task_supersede`(`:927`)
- **软模式定义**：只**告警**不拒绝——缺 dispatch 时回执附提示，不破坏现有调用方
- 落点：`server-reg-task.js` 单文件
- **验证**：`node resources/memoryos/dist/smoke-task.js` 全绿 + 新增 T8j–T8o 用例
- **权衡**：软模式零破坏但收益低；强模式收益高但要等软跑一批（G6）

### 批次 A3｜`task_heartbeat` 承载 `fenced` 位

> 依据 §4 P0-3

- 现状：`consumer_fenced` 是 worker 得知"已被取代"的**唯一途径**，但 MemoryOS 无主动通道
- 做法：heartbeat 回执带 `fenced: true/false`（内部用 `readActiveDispatch` 比对 generation）
- **验证**：新增 T8p——换代后旧 dispatch 的 heartbeat 应回 `fenced`

### 批次 A2｜`task_next` 增"待决策 dispatch"段

> 依据 §4 P1-3

- 落点：`server-reg-task.js:969`
- 做法：`task_next` 输出增一段"待决策 dispatch"（`state='stale'`，或 `settled` 但未 release 的）
- **验证**：构造 stale dispatch → `task_next` 应列出

### 批次 B1｜reaper 改"只标不回收"（中风险，动守护进程）

> 依据 §4 P0-1，**本计划最重要一条**

- 现状：`daemon.js:688-754` 两阶段——阶段①`:694-701` 贴条（`lease_notice_at`）→ 阶段②`:704-737` 贴条超 grace（`MEMORYOS_LEASE_GRACE_HOURS` 默认 24h，`:690`）后**直接回收**（任务 `in_progress`→`pending` + 卡 `status='ready'`、`assignee=NULL`、`claim_lock=NULL`）
- Orca 判据：**只有正面退出证明才授权停止/放弃/重试；缺席（absence included）也是检查点**
- 做法：阶段② 改为**只标 `state='stale'`**，**不回收**；回收需正向动作（新 dispatch 接管 / 人工裁决 / 显式 release）
- 同款需同步：`dashboard-reg-cards.js:1286-1304`
- **代价（须你知晓）**：卡不再自动回到 `ready` → 必须配一条"裁决入口"，否则积压（见 G2）
- **验证**：回归 `smoke-daemon.js` + 构造过期租约用例，断言"不再自动回收"
- **可逆**：改动前记 SHA256，回滚 = 还原文件

### 批次 C2｜截断契约扩面（低风险）

> 依据 §10.6 P1-11

- 现状：只有"语义降级"一类告警（`server-reg-memory.js:249-252`，做得对，值得扩面）
- 新增 3 类告知：候选集被截（`candidates`）、snippet 被缩（`snippets`）、查询被切（`query`）
- **验证**：构造超候选集查询，回执应含提示

### 批次 B2｜分区 `state` 化（中风险）

- **验证**：模板自查 + 后续会话按新字段登记

### 批次 D1｜`request_id` 幂等（中风险，新表）

> 依据 §4 P2-1 / P1-8

- 场景：接管 / 重放需要 at-least-once + 幂等

### 批次 C3｜检索 cursor 分页（可选，建议后置）

> 依据 §10.6 P1-10

## 4. 明确不做（YAGNI，避免过度工程）

| 不做 | 理由 |
|---|---|
| 跨主机 `hosts[]` 七态 / `executionHostId` | MemoryOS 单机部署，无此场景 |
| AI Vault 式"转录索引" | 目标不同：Orca 索引会话历史，MemoryOS 索引结构化条目 |
| typo 修复 / planner route 对调用方暴露 | 收益不明，先观测 |
| `evidence` / `presence` 照搬 | MemoryOS 无转录层，**须按自己语义裁剪** |
| 新框架 / 新检索后端 | 超出需求范围（最全改动≠无边界扩面）；现有 RRF + FTS5 + 向量已够 |
