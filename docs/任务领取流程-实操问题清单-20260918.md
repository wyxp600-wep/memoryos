## 1.【P0】按 id 的任务操作**绕过归档守卫** → 可领到已归档/已合并的任务

**事实**
- 列表分支有列过滤：`task_next` / `task_claim`（无 id 分支）用
  `WHERE type='task' AND status IN ('active','trial') AND ... sensitivity != 'secret'`
  （`server.js:1124-1126`；`task_next` 同口径）
- **按 id 的直接分支只读头文本**：`task_claim` 用 `readMemory(db, args.memory_id)` 后仅判
  `st.status !== "pending"`（`server.js:1096-1103`）；`task_done` 同（仅 `st.status==='done'` + `assertTransition`）
- 而 `readMemory` 是 `SELECT ... WHERE id = ?`，**无 status 过滤**（`db.js:1089-1092`）

**实测数据**（生产库，`type='task'` 共 114 条）

| 头文本 status | 列 status | 条数 |
|---|---|---|
| pending | **archived** | 27 |
| pending | **merged** | 2 |
| done | archived | 31 |
| pending | active | 26 |
| done | active | 18 |
| archived | archived | 7 |
| done / in_progress | merged / archived / active | 3 |

⇒ **29 条**任务头为 `pending` 但列已归档/已合并（例：#4256、#4257 列=merged；#4101–#4104、#4136–#4145、#4210–#4224 列=archived）。

**后果**：这些任务不会出现在 `task_next` 可做集（被列过滤挡住），但
`task_claim(memory_id=4256)` **会成功**（只判头文本 `pending`）→ 领到一条已被取代/已归档的任务。

**说明**：我**未实际执行**该领取（避免污染生产），结论来自代码路径 + 数据分布；如需实证可在临时库复现。

**修法**：按 id 分支补一行列守卫：
```js
if (!["active", "trial"].includes(row.status))
    return `#${row.id} 已${row.status === "merged" ? "被取代" : "归档"}，不可领取/完成。`;
```

## 2.【P0】`task_supersede` 只改列不改头 → 其宣称的「移出可做集」不成立

**事实**
- `task_supersede` → `markMerged(db, loserId, winnerId)`
- `markMerged` 只执行 `UPDATE memories SET status='merged', superseded_by=? WHERE id=?`
  （`db.js:1527-1530`），**完全不触碰 `[status:]` 头文本**
- 同理 `setStatus` 也只改列（`db.js:1633-1641`）

**实测**：#4256 / #4257 列=`merged`，头仍是 `pending`。

**后果**：与问题 1 叠加 → **被 `task_supersede` 合并掉的任务仍然可被 id 领取**。工具描述里「状态置 merged ⇒ 移出可做集」只在"走列表接口"时成立，在"按 id"时不成立。

**修法**：`markMerged` 同步重写头文本为 `merged`（并纳入问题 3 的状态机白名单）；或至少在 `task_claim`/`task_done` 里补列守卫（= 问题 1 的修法，二者修一个即可堵住）。

## 4.【P1】`pending → done` 被拒 → 收口必须「伪造领取」，**污染审计**

**事实**
- 实测：`task_done(#4198)` → `非法状态迁移 pending → done（白名单: in_progress, cancelled）`
- 只能先 `task_claim`（改写 assignee `?`→`workbuddy`、发租约、version+1）再 `task_done`（version+1）
- 4 条任务 = **8 次状态写入 + 8 条事件**，全为噪音

**事实对照**（关键）
- C-2…C-5 的真实实施是提交 `1ac7f5d`（**2026-09-16 19:24**，作者 `wyxp600`）
- 而事件流现在写的是 **2026-09-18 14:46 `task_claim by workbuddy` + `task_done by workbuddy`**

⇒ **归属与时间全错**。`task_claim` 事件从此不再等于"谁做过这件事"，审计链被自己人污染。若这是常态，`task_claim` 事件的价值归零。

**修法**：加 `task_verify` / `task_close`（第三方验收关闭：改状态头 → done，**不改 owner、不发租约、不写 claim 事件**，只写 `verified_by`）；或允许 `pending → done` 但强制带 `reason` + 证据。

## 10.【P1】写入类工具返回「人话」而非可校验终态 → **静默失败**难发现

**事实**：`memory_write(supersedes=4309, version=…)` 返回
> 已写入记忆 #4311（⚠ 疑似与 #4252 冲突，置信 0.5，待 v0.3 仲裁）

而 `supersedes` **完全没生效**：旧条不归档、`superseded_by=NULL`、无 `superseded` 事件、`causal_parent=NULL`。我是**事后查库**才发现的（详见 `P2-5-C1-验收复核-20260918.md` §4.1 / 记忆 #4312）。

**后果**：这是最危险的失败形态 —— **成功回执 + 零副作用**。任何依赖回执的自动化都会以为成功。

**修法**：写入类工具返回结构化终态（`{id, status, superseded_by, causal_parent}`）；或至少在回执里显式声明「supersedes 已应用 / 已跳过（原因）」。
