# 减少大模型读取记忆时的 token —— 实测与优化方案

状态：**待授权**（本文档只做实测与设计，未修改任何源码）
日期：2026-10-11
数据源：生产库 `%APPDATA%\MemoryOS\data\memory.db`（active 1793 条）+ `dist/*.js` 读码

---

## 1. 实测：token 花在哪里

| 项 | 字符 | ≈token | 频率 | 说明 |
|---|---|---|---|---|
| **MCP 工具 schema**（26 工具 description + 参数 describe） | **4947** | **~3.4k** | 每会话固定 | memory 11 + task 12 + obsidian 3；进 system prompt，无法按需省 |
| `memory_context`（limit=5） | 1630 | ~1.1k | 每次注入 | 记忆行 850 / scope 列表 266 / 围栏 214 / 标题+用法 ~300 |
| `memory_search`（limit=10） | 5530 | ~3.9k | 每次检索 | 命中行 2680 / **证据块 2350** / 尾注图例 ~500 |

库内 active 正文长度：**p50=120 / p75=452 / p90=954 / p99=2103 / max=5231**；>120 字占 **50%**，>220 字占 **35%**。

典型会话（1 次 context + 3 次 search）≈ **3.4k + 1.1k + 3×3.9k ≈ 16.2k token**，其中记忆相关约 13k。

### 最大单点浪费：证据块（占单次 search 的 42%）
`evidenceSnippet`（`server-reg-memory.js:36-51`）从**同一份扁平正文**再截 120 字，围绕查询词定位；而命中行已截前 220 字。
- 查询词位于前 220 字内 → 两者内容重叠，**纯冗余**
- 只有查询词位于 220 字之后 → 证据块才有增量价值
实测 10 条命中全 >220 字 → 证据块 2350 字符，多数无增量。

## 2. 优化清单（按收益/成本排序）

### P0 零风险、改动小
| # | 措施 | 改动点 | 收益 | 风险 |
|---|---|---|---|---|
| 1 | **证据块条件化**：仅当命中词位置 ≥ SNIPPET_MAX 时输出 | `server-reg-memory.js:485-487` + `evidenceSnippet` 返回位置 | search −1.5k token/次（−38%） | 极低（后段关键词仍保留） |
| 2 | scope 列表压一行（`global(1562) memoryos(67) …`）+ 用法说明压成 1 行 | `:687-698` | context −0.25k token/次 | 无（信息不丢） |
| 3 | **同 session 注入去重**：内容 hash 未变 → 返回「内容未变，沿用上次注入」 | `:639-698`（按 session_id 缓存 hash） | 重复调用时 −100%（实测单轮会话调了 3 次） | 低（需 session_id，未传则退化为现状） |

### P1 固定开销（一次生效，每会话都省）
| # | 措施 | 改动点 | 收益 | 风险 |
|---|---|---|---|---|
| 4 | **低频工具 schema 二次瘦身**：参数 describe 压到 ≤20 字，详规全走 `tool_guide`（机制已存在） | `server-reg-memory.js` / `server-reg-task.js` 的 `.describe()` | −1.5~2k token/会话 | 中：agent 不查 tool_guide 会用错参数 → 只压低频工具（task_heartbeat / task_verify / memory_credential / memory_report / memory_feedback），高频工具保留必填说明 |

### P2 结构性（收益最大，改变调用习惯）
| # | 措施 | 做法 | 收益 | 风险 |
|---|---|---|---|---|
| 5 | **用 `memory_ask` 替代 `memory_search`** | 服务端 LLM 读记忆后只回答案（`max_tokens=600` ≈900 字符） | 主模型侧 −60~80%/次 | 答案有 LLM 二次加工；要原始列表仍需 search |
| 6 | 渐进披露：search 默认 10 条只展开前 5 条，其余仅 `#id [type] 首行40字` | `:476-492` | −1.2k token/次 | 需要时多一次 `memory_read` 往返 |
| 7 | context 默认 limit 5 → 3 | `:634` | −0.4k token/次 | 注入覆盖面略降 |

### P3 治本
| # | 措施 | 说明 |
|---|---|---|
| 8 | 写入侧长度建议：正文 >600 字时回执提示精简 | 库 p90=954 字，大量记忆含过程复述；同时降低注入、检索、向量三重成本 |
| 9 | 冗余记忆合并（见 `merge-similar-plan.md`） | 条数减少线性降低注入/检索 token；与 1-3 叠加效果最好 |

---

## 3. 不建议做
- 截断阈值降到 <100 字（p50 正好 120，会直接损失信息）
- 删不可信围栏（214 字符/次，是注入防御边界）
- 删 scope 列表（会漏检，压成一行即可）

---

## 4. 推荐组合与预期

若实施 **P0 全部 + P1 第 4 项**：
- 每会话固定：−1.5~2k
- 每次 search：−1.5k
- 每次 context：−0.25k（重复调用再 −1.1k）

典型会话 **16.2k → ~9k token（省 ~44%）**，且不损失任何记忆信息（只删冗余重复片段）。

## 5. 验证方式（每项改完必跑）
1. 门禁四件套：`lint-sql-arity` / `lint-silent-catch` / `snapshot-routes --check` / `smoke-all`（基线 22 PASS）
2. 字节级对比：改动前后各跑一次同 query 的 search，`wc -c` 对比输出字符数（预期下降且无信息缺失）
3. 断言证据块保留条件：构造一条"关键词在后段"的记忆，确认仍输出 `↳ 证据`；关键词在前段则不再输出
4. `node --check` 语法 + 托盘重启内核后复测
