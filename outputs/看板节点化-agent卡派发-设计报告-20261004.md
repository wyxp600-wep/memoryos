> 需求来源：用户口述 —— 看板升级为 ComfyUI 式节点画布；节点分「任务卡」与「Agent 卡」两类，可自由添加、随意拖动；连线即派发；任务完成后生成交接文档卡，供后续 Agent 卡无缝接续。

## 1. 结论先行

1. **需求可落地，且现有地基覆盖约 70%**：卡片拖拽 + 位置持久化、卡片图（节点+边）、A1 一键派发全链路（dispatch 原语 + 唯一 active 约束 + fencing）、task_done 结论回写与卡片联动均已存在。
2. **核心增量是三块**：① Agent 卡（含三通道执行层：CDP 直控 / UIA 驾驶 / MCP 队列）；② 交接文档卡（handoff，现有近似物只有 conclusion 回写，无显式交接结构）；③ 画布升级（从"任务地图"静态图升级为可自由增删节点、连线的 ComfyUI 式编辑器）。
3. **软件式智能体可以逼近终端式体验**（工作区/模型/配置 + 后台点火 + 画面直播），靠的是 Electron/VS Code 分叉应用可被 CDP/UIA 驾驶这一事实，代价是选择器脆弱性与灰色自动化，需用"档位诚实标注"对冲。
4. **两个待拍板点**：画布自研 SVG vs 引图库（本报告推荐自研轻量 SVG）；Agent 卡执行层按三通道适配（本报告推荐）还是纯 MCP 队列（不满足"软件直接操作智能体"的原始需求）。

## 3. 总体架构

```
┌────────────────────────── 看板前端（画布编辑器） ──────────────────────────┐
│  节点面板（任务卡｜Agent卡）  画布拖拽/连线  卡片详情抽屉  内嵌直播区/终端区   │
└───────────────┬──────────────────────────────────────────┬───────────────┘
                │ REST/SSE（既有 8787 Dashboard）            │
┌───────────────▼──────────────────────────────────────────▼───────────────┐
│  执行编排层（新增 executor 模块，随 dashboard.js 加载）                      │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────────────────────────────┐  │
│  │ 通道① CLI直控 │  │ 通道② CDP/UIA │  │ 通道③ MCP 队列（现有 A1 链路复用） │  │
│  │ spawn headless│  │ 驾驶 Electron │  │ task_assign → 对方领单 → done 回写 │  │
│  │ 参数=四项配置  │  │ /VSCode 分叉  │  └──────────────────────────────────┘  │
│  │ SSE→终端区    │  │ 点火+screencast│                                        │
│  └─────────────┘  └─────────────┘                                          │
│  统一接口：run(agentProfile, task, opts) → RunHandle{stream, status, result}│
└───────────────────────────────────────────────────────────────────────────┘
```

**设计原则**：
- **一张卡统一形态，底层三通道适配**：用户不感知通道差异，卡片上如实标注档位（沿用驾驶舱"诚实 stub"政策）。
- **卡片零权威**：所有执行权威仍在 `dispatches`/`agent_runs` 表，卡片只是投影（现有 `claim_lock` 投影设计直接沿用）。
- **结果回收与过程直播分离**：结果一律走可靠通道（CLI 输出落盘 / MCP task_done 回写），直播（SSE/screencast）只做可视化，不承载结果。
- **可回滚硬边界**：新表只增不改；画布 UI 是前端增量，`meta.map_pos` 格式不变；执行编排层为独立模块，不侵入现有 dispatch 原语。

## 4. 任务卡设计

### 4.1 数据模型（增量）

`cards` 表不动，用 `meta` 承载扩展字段（沿用 `meta.map_pos` 先例）：

```jsonc
// cards.meta.task_ext
{
  "skills": ["spec-coding", "code-review"],   // 挂载技能（知识库 slug 或 SKILL.md 路径）
  "aids": ["card:1234", "memory:456", "file:D:/.../context.md"],  // 辅助信息引用
  "handoff_in": "card:1301",                  // 挂接的上游交接卡（创建时可选）
  "acceptance": "npm test 全绿"               // 可选验收标准
}
```

### 4.2 行为

- **用户创建**（2026-10-04 二次修正：**先建卡、后选型**）：节点面板拖入"＋ 卡片" → 画布落下中性**文档卡**（默认 `kind='doc'`，不进任务状态机）→ 用户在卡片上的类型徽标处改选类型（任务 / Agent / 交接 / 文档 / 自定义）。类型切换走新增端点 `POST /api/cards/:id/retype`（守卫见 §7.3）；之后详情抽屉填写标题/描述/技能/辅助信息。
- **Agent 创建**：复用 `task_assign`（MCP）或现有建卡端点，来源标注沿用既有规则（`[卡片#N]` / `[agent任务]`）。
- **技能加载**：派发时把 `skills` + `aids` 渲染进任务正文（MCP 通道）或启动参数/prompt 前缀（CLI/CDP 通道）。辅助信息若指向库内记忆/卡片，先 `memory_read` 展开为文本，避免下游 agent 二次检索失败。

## 5. Agent 卡设计（核心）

### 5.1 数据模型

新增轻量表（不碰现有表结构，可回滚 = drop 即回退）：

```sql
CREATE TABLE agent_profiles (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,            -- 卡片显示名
  agent_key TEXT NOT NULL,       -- 对应 scanAgents() 的 key（codex/zcode/traecode/...）
  channel TEXT NOT NULL,         -- 'cli' | 'cdp' | 'uia' | 'queue'
  workspace TEXT,                -- 工作区绝对路径
  model TEXT,                    -- 模型名
  context_tokens INTEGER,        -- 上下文配置
  reasoning TEXT,                -- 推理强度（minimal/standard/extended 等，按 agent 枚举）
  launch_overrides TEXT,         -- JSON：各通道启动参数模板（选择器/驱动描述文件也放这）
  meta TEXT
);
```

### 5.2 卡片 UI 形态

> **诞生路径（先建卡后选型）**：任何卡片都可经卡上类型菜单切换为 Agent 卡——切换时弹出配置向导（从 `scanAgents()` 结果选智能体 → 填工作区/模型/上下文/推理强度 → 建 `agent_profiles` 行并回填 `meta.profile_id`）。反方向切换（Agent→其他）须确认删除 profile，且卡上有 active run/dispatch 时拒绝。

```
┌─ Agent 卡 ────────────────────────┐
│ ● zcode-cli        [直控·满血]     │  ← 状态灯 + 档位徽标（诚实标注）
│ 工作区: D:\proj\foo                │
│ 模型: glm-5.3  推理: standard      │
│ 状态: 正在执行 任务#123 (心跳 2m)   │  ← 读 dispatches + agent_runs，卡不自己探测
│ ┌─ 直播区 ──────────────────────┐ │
│ │ (终端流 / screencast 帧 / 状态)│ │  ← 通道①SSE终端流；通道②screencast；通道③仅状态
│ └───────────────────────────────┘ │
│ [配置] [执行] [停止]  入边×2 出边×1 │
└───────────────────────────────────┘
```

### 5.3 三通道执行层（关键）

统一接口 `run(agentProfile, task, opts) → RunHandle`，按 `channel` 分发：

**通道① CLI 直控（终端式智能体：codex/claude/zcode-cli/aider/gemini 等 7 个）**
- 实现：`spawn`（异步，禁 spawnSync——已有踩坑记忆）拉起 headless 命令；`cwd=workspace`，`--model`/`--reasoning` 等映射四项配置；stdout/stderr 接 SSE 回填卡片终端区（复用 `/api/exec/stream` 模式）。
- 凭据：沿用各 agent 现有登录态/凭据体系（如 Claude Code 的 DPAPI 凭据管理器），**执行层绝不新增密钥存储**。
- 超时/取消：RunHandle 带 kill；超时写 `agent_runs` 终态。

**通道② CDP/UIA 驾驶（软件式 Electron/VS Code 分叉：zcode 桌面、traecode、traework、workbuddy 等）**
- 配置：启动前写其本地配置或带参拉起（如 VS Code 系 `<exe> <workspace>` 直接定工作区）。
- 点火：Electron 加 `--remote-debugging-port=<独占端口>` 启动 → CDP 在 renderer 找输入框 DOM 注入任务文本；非 Electron 或未开调试口 → UIA 无障碍树找控件发文本（可复用 orca computer 基础设施）。
- 直播：CDP screencast 帧流 → 卡片内嵌画面；降级为截图轮询。
- 驱动描述文件：DOM 选择器/控件路径做成 `launch_overrides` 里可热修的 JSON，App 更新断选择器时不用改代码。
- 结果回收：**不从界面抓结果**，让 App 内智能体走已配置的 MemoryOS MCP `task_done` 回写（可靠通道），执行层只等 dispatch 收口。

**通道③ MCP 队列（保底，纯复用）**
- 即现有 A1 链路：`POST /api/cards/:id/dispatch-agent` → `createDispatch` → 对方领单 → `finalizeCardDispatch` 收口。零新代码，只是 Agent 卡的派发按钮改为落到这条链。

**通道探测**：添加 Agent 卡时调 `scanAgents()` 结果 + 一次 CDP 端口探测，自动定档；档位徽标如实显示（满血/残血/保底）。

### 5.4 "显示对应打开的智能体"

- 通道①②：执行编排层自己拉起的进程，句柄在手——状态（启动中/运行/空闲/退出）、PID、运行时长直接可知。
- 通道③：读 `dispatches`（active dispatch 归属 + `heartbeat_at`）+ `agent_runs` 状态，卡片显示"谁正在干哪个任务、心跳多久前"。
- 统一由后端聚合一个 `GET /api/agent-cards/:id/state` 端点，卡片只读此端点，**严禁前端自行探测进程**（避免与看板单一事实源打架，遵守"任务统一看板展示"既有约定）。

## 6. 连线派发 + 交接文档卡

### 6.1 连线即派发

- 画布上从任务卡出边到 Agent 卡入边 → 前端确认弹层 → `POST /api/cards/:id/dispatch-agent`（body 附 `agent_profile_id`）。
- 后端改造点（小）：dispatch-agent 接受 `agent_profile_id`，按通道①②时改为调用执行编排层（建 `agent_runs` 记录 + dispatch 工作证照旧生成，保证 fencing/唯一 active 语义**全部保留**）；通道③走现有逻辑不动。
- 一条边 = 一次派发尝试，历史留 `dispatches.generation` 链；重复连线复用幂等语义。

### 6.2 交接文档卡（handoff）

**生命周期**：
1. **生成**：run 终态收口时（`finalizeCardDispatch` / CLI 进程退出 / task_done 回执），把结论结构化落成一张 `kind='handoff'` 卡：
   ```
   ## 交接文档 · 任务#N
   - 做了什么（结论摘要）
   - 改了哪些文件/关键决策
   - 踩坑与规避
   - 遗留与建议下一步
   - 产物指针（分支/文件/记忆 id）
   ```
   来源优先级：CLI 通道 = 模型输出的最后一段结构化摘要（prompt 里约定格式）；MCP 通道 = `task_done.conclusion` + 任务正文；CDP 通道 = MCP 回写为主、界面文本兜底。
2. **挂边**：handoff 卡经 `card_memory(relation='handoff')` 同时连到原任务卡（产出）——沿用 aux_memory 挂图机制（`dashboard-reg-cards.js:1049`），在画布上自然可见。
3. **消费**：后续任务卡连到该 handoff 卡（或建任务时选"继承交接"）→ 派发时执行层把 handoff 全文注入任务正文头部（"前情提要"段），下游智能体开局即有上下文。
4. **防打架**：handoff 卡是纯文档卡（kind='handoff'，不进任务状态机），不参与 claim/dispatch 对账；图对账时按既有经验排除辅助类节点（参考 #4192 教训：辅助/归档节点不得混入真任务统计）。

## 7. 画布编辑器（ComfyUI 层）

### 7.1 权衡：自研 SVG vs 引图库

| 维度 | 自研轻量 SVG（推荐） | 引 Vue Flow / LiteGraph |
|---|---|---|
| 节点规模 | 看板几十张卡，性能无忧 | 为千节点设计，过剩 |
| 样式一致性 | 直接沿用现有卡片 DOM/样式，改造量小 | 需重画节点外观 |
| 连线交互（吸附/避让/缩放） | 全部自写，工作量主要在这里 | 现成 |
| 新依赖/回滚 | 零依赖 | 引依赖，样式深度定制成本 |
| 现有资产复用 | `dragTaskMapNode`、`#taskMap` DOM、`meta.map_pos`、SSE 重画全部保留 | 推倒重来 |

**推荐自研**：现有任务地图已是"世界层+边层+节点层"三件套（`index.html:4749-4777`），升级为编辑器 = 加"节点面板拖入创建 + 边拖拽 + 框选/缩放"三件事，比引库重画划算。

### 7.2 交互规格

- **添加节点**（2026-10-04 修正）：左侧节点面板只有**一个"＋ 卡片"入口**，拖入画布即落一张中性文档卡；类型在卡片生成后于卡上徽标处选择。落点即 `meta.map_pos`。
- **卡上选型**：点类型徽标弹菜单（内置：任务 / Agent / 交接 / 文档 + 自定义类型 + "新建类型…"），见 §7.3。
- **连线**：节点端口拖出贝塞尔边；任务卡→Agent 卡 = 派发边（带确认）；任务卡→handoff 卡 = 继承边；handoff 卡→任务卡 = 前情注入边。非法方向（如 Agent→Agent）拖拽时即禁用。
- **拖动**：复用 `dragTaskMapNode` + `POST /api/cards/:id/position`。
- **实时**：沿用 `/api/cards/stream` SSE，800ms 防抖重画；直播区独立小流，不触发全图重画。

### 7.3 自定义卡片类型（2026-10-04 新增，用户需求：可自建想要的卡片类型）

**类型注册表** `card_types`（新表，drop 即回滚；内置四种种子，系统类型不可删改）：

```sql
CREATE TABLE IF NOT EXISTS card_types (
  type_key   TEXT PRIMARY KEY,      -- 'task'|'agent'|'handoff'|'doc'|用户自定义 key
  label      TEXT NOT NULL,         -- 显示名
  color      TEXT,                  -- 徽标色
  builtin    INTEGER NOT NULL DEFAULT 0,
  can_dispatch_out INTEGER NOT NULL DEFAULT 0,  -- 可发起派发边（task=1）
  can_dispatch_in  INTEGER NOT NULL DEFAULT 0,  -- 可接收派发边（agent=1）
  can_inject_out   INTEGER NOT NULL DEFAULT 0,  -- 可发起注入边（handoff=1）
  can_inject_in   INTEGER NOT NULL DEFAULT 0,  -- 可接收注入边（task=1）
  meta       TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

- **行为即端口**：连线的方向校验从"写死矩阵"改为按类型行为档位判定——派发边要求 `source.can_dispatch_out && target.can_dispatch_in`，注入边同理。自定义类型默认全 0（纯文档节点，不参与任何边），用户在"新建类型…"编辑器里命名、选色、按需勾选端口角色。
- **保留命名空间**：自定义 `type_key` 禁止使用内置四种及 `aux_` 前缀（防与图对账排除逻辑冲突），服务端校验。
- **retype 端点**（先建卡后选型的必需件，已实证 `PUT /api/cards/:id` 不支持改 kind）：`POST /api/cards/:id/retype {kind}`，守卫——卡片 running 或存在 active 派发边时 409；切入 `agent` 走配置向导；切出 `agent` 确认删 profile；切入 `task` 自动置 `status='triage'` 进任务状态机。
- **中性默认**：新建卡一律 `kind='doc'`，避免默认落进任务状态机（现 `POST /api/cards` 缺省 kind='task'，需改默认值——这是对既有端点唯一的行为变更，回滚点明确）。
