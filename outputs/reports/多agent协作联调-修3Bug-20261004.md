## 结论（核心）

端到端测试「多 agent 协作功能」（两层探针，全确定性、临时库、不碰生产）一次性暴露 **3 个真 Bug**，全部修复并过六门禁：

1. **`TxAbort` 漏注入**（P2-3 拆分搬移遗留）
   - `server-reg-task.js` 内 7 处 `throw new TxAbort(...)`，但共享名经 ctx 注入、`server.js:149` 的 ctx 字面量漏了 `TxAbort` → 并发认领冲突时全变 `ReferenceError: TxAbort is not defined`（事务仍回滚数据无损，但 agent 拿到内部错误而非设计文案）。
   - 修：ctx +解构 各 1 项（与既有注入模式同款）。

2. **`handle.ev` 签名不匹配 → run 内 `task_done` 成功即崩 run**（pre-existing，高危）
   - `agent-runs.js` `createRun` 返回**裸 3 参** `ev(run,type,data)`，而路由侧一律按 2 参 `handle.ev(type,data)` 调（`getRun` 返回的本就是包装版）→ `task_done` 成功回执一到，`run.seq += 1` 作用在字符串 `'task_done'` 上抛 `Cannot create property 'seq'` → 整个 run 崩。此前 LLM 不可用故从未踩中，A1 收尾轮首次实测暴露。
   - 修：`createRun` 返回 `ev: (type, data) => ev(run, type, data)`（与 `getRun` 同款）。全仓 `.ev(` 仅 2 处调用方、均 2 参，无 3 参依赖。

3. **缺 `card_memory('dispatch')` 行 → done 头被收口投影回 `in_progress`**（生产可达）
   - `from-memory` 建的卡关系是 `'reference'`、`import-legacy` 无关系行；`task_done` 的 `syncTaskToCard` 只认 `relation='dispatch'` → run 内完成后卡仍 running → A1 收口 running→review → `syncCardToTask` 经 E-0 映射（review→in_progress）**把 done 头改回 in_progress**（权威源被污染）。
   - 修：`dispatch-agent` 认领事务内幂等 `INSERT OR IGNORE card_memory(...,'dispatch')`（`task_assign` 本就双写；PK 含 relation 不与 reference 冲突）。

## 关键坑（测试方法论）

- **双 MCP 实例不可同时 `openDb` 同一新库**：`PRAGMA journal_mode=WAL` 互锁 → `database is locked` 崩掉、initialize 超时（时序运气，前两次恰好错开）。**顺序启动**（A init 完再 spawn B）。
- **假 LLM 分支匹配要用原始 body**，不能 `JSON.stringify(messages)`（把提示词里的 `"` 转义成 `\"`，正则 `dispatch_key="..."` 必漏配）。
- **造排队窗口**：假 LLM 加 1500ms 延迟，否则本地响应太快、串行派发全 running 零 queued。
- dashboard MCP 身份固定 `dashboard-agent`（`getAgentMcp` agentName），工作证 agent 与其不一致时 run 内 `task_done` 被 fencing 拒（软模式回执、不崩）——派发关联任务卡应传 `agent:"dashboard-agent"`。
- 探针断任务头/卡片终态，禁取中间态；`card_memory` 只有 task_assign/daemon/from-memory 三类写入方。
