## 四、修复方案（按权衡排序）

### 方案 A：记忆为真相源 + 自动同步（推荐）

**做法**：`cards.status` 从 `memories.content` 状态头派生，`memory_write(type=task)` / `task_assign` / `task_claim` / `task_done` 内自动 upsert cards 行。

| 维度 | 评估 |
|---|---|
| 改动量 | 中（server.js 4 处 + dashboard.js 加同步函数） |
| 一致性 | ★★★ 单一真相源 |
| 风险 | 需处理历史 27 条重复导入（ref_id 唯一索引） |
| 收益 | 彻底消除双状态机漂移 |

### 方案 B：加同步钩子 + 定时兜底（折中）

**做法**：写 memories 时触发 upsert；另加 `daemon.js` 每 N 分钟跑一次 `import-legacy` 增量。

| 维度 | 评估 |
|---|---|
| 改动量 | 小 |
| 一致性 | ★★ 有窗口期 |
| 风险 | 低，可回退 |
| 收益 | 快速打通，隐患仍在 |

### 方案 C：前端自动调用（最省）

**做法**：地图视图 `renderTaskMap()` 前自动 `POST /api/cards/import-legacy`。

| 维度 | 评估 |
|---|---|
| 改动量 | 最小（1 行） |
| 一致性 | ★ 每次刷新全表扫 |
| 风险 | 性能，且状态仍不同步 |
| 收益 | 仅解决"看不见" |

**建议**：先做 **方案 C 止血**（1 行，立即可见），再排期 **方案 A 治本**。

## 八、地图 → MCP 反向同步（2026-09-13 00:30 ~ 00:45）

### 缺口

此前只有**单向同步**（记忆头 → cards）。人在看板/地图拖卡改状态、认领、改标题后只写 `cards`，
记忆头不变；下一次 `syncTaskCards()` 又用记忆头旧值**覆盖回去** → **人的操作被静默丢弃**。

### 用户决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 同步范围 | **写时回写 + 手动修复接口** | 避免与 MCP 侧写入乒乓；无冲突裁决歧义 |
| 标题变更 | 写回记忆头正文 | 行为一致 |
| `[by:]` 段 | 写 `[by:human]` | 保留「谁改的」语义 |

### 冲突裁决：为什么不做时间戳比对

| 候选 | 否决原因 |
|---|---|
| `updated_at` 新者胜 | `memories` **根本没有 `updated_at` 列**；且 cards 用 `strftime`、memories 用 `datetime`，格式不可比 |
| 人优先 | MCP 侧 agent 动作会被人的旧操作反覆盖 |
| **事件驱动（采用）** | 只写「刚发生的这次变更」，无时间戳、无歧义；历史漂移交给手动接口修复 |

### 实现（`dist/dashboard.js`）

| 项 | 内容 |
|---|---|
| `CARD_TO_TASK` | cards 十态 → MCP 七态：`triage/todo/ready→pending`、`running→in_progress`、`review/blocked/failed/done` 同名、`cancelled/archived→cancelled` |
| `pushCardToTask(cardId, patch)` | 核心回写；复用 `updateMemory()` 保证 FTS + 2-gram + 向量缓存同步 |
| `pushAllCardsToTasks()` | 手动全量对账（以 cards 为准） |
| 挂接写入路径 | `POST /api/cards/:id/status`、`/claim`、`PUT /api/cards/:id` |
| 新增接口 | `POST /api/cards/push-to-tasks`（全量）、`POST /api/cards/:id/push-to-task`（单卡） |
| `/api/tasks` | 新增 `claimedBy` 字段 |

### 踩坑（三处臆造 + 两处真 bug）

| # | 坑 | 处理 |
|---|---|---|
| 1 | 臆造 `refreshFts()` | 不存在。复用 `db.js` 的 `updateMemory()` |
