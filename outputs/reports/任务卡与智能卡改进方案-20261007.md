## 一、状态设计

### 1.1 现状：10 态全梳理

| 状态 | UI 名 | 业务含义 | 进入条件 | 流转触发 | 终态？ |
|---|---|---|---|---|---|
| triage | 待细化 | 待 LLM 分流/细化（服务采集导入链路） | 创建时未显式传 status（**人工建卡也被默认落此**） | 调度器超 24h 自动→todo；人工 /status | 否 |
| todo | 待就绪 | 已明确要做，等依赖满足 | triage→todo | 依赖满足时派发/调度**自动**→ready；人工 /status | 否 |
| ready | 可认领 | 依赖满足，随时可认领/派发 | todo→ready | 派发/人工认领 CAS→running | 否 |
| running | 执行中 | 持有 active 工作证（dispatches 租约 10min） | 派发/认领 | run 终态回调→review / failed | 否 |
| review | 待验收 | 执行成功，等人工验收 | finalizeCardDispatch | 人工 /accept（带验收卡不许 /status 直达 done，cards.js:929-936） | 否 |
| done | 完成 | 验收通过 | review→done | 人工→archived | 终态① |
| failed | 失败 | 执行失败，failure_count+1 | running/review→failed | ≥2 次调度器熔断→blocked；可人工重开 | 否 |
| blocked | 阻塞 | 外部原因挂起 | todo/running/failed→blocked | 人工解除→todo/ready | 否 |
| cancelled | 取消 | 主动放弃 | 多态可达 | — | 终态② |
| archived | 归档 | 清理出活跃面 | done→archived | — | 终态③；/api/cards 默认剔除 archived/cancelled（cards.js:597-600） |

地图侧另有简化分桶 `statusBucket`（app.js:4553）：done=已完成 / running=已领取 / archived+cancelled+failed=已归档 / 其余=未完成。

### 1.2 为何「建卡后必须手动切状态才能派发」

三个默认值/预检叠加的产物，**不是状态机的必要约束**：

1. 前端建卡不传 status → 后端默认落 `triage`（cards.js:651）；
2. 前端派发预检只放行 `todo/ready`（app.js:6471-6480），triage 卡点 ⚡ 被拦，提示「先把状态流转过去再派」；
3. 后端派发路径只对 `todo` 自动升 `ready`（cards.js:764-768），`triage` 不在派发路径上——只有顶栏调度器在超 24h 后才兜底升档（cards.js:1650-1658）。

用户刚亲手填完标题建好的卡，却被标成「待细化」并挡在派发门外——这一步人工介入没有任何信息增量：**人在建卡时已经完成了分流**。

### 1.3 现状问题

- **P0 级默认值错位**：`triage` 的语义是「待 LLM 分流」，属于采集/导入链路；人工建卡继承这个默认值是张冠李戴，制造了唯一的强制手动流转步。
- **todo/ready 对用户是冗余概念**：「依赖是否满足」是系统可自动推断的隐式信息（派发时自动升档已实现），却作为两个看板列暴露给小白，需要解释成本。
- **终态三层偏重**：done/archived 两层 + cancelled，对个人用户而言 archived 的独立价值只在「清理活跃面」，可以弱化展示但底层数据保留。
- 状态机本身（CAS + 迁移白名单 + 工作证联动）是资产，**不建议删态**，建议收敛的是默认值与展示层。

### 1.4 改进建议

1. **人工建卡默认 `status='todo'`**（改 cards.js:651 一处 + 前端预检文案同步）。`triage` 仅由采集/导入链路显式写入；调度器的 24h 自动升档保留作为采集卡兜底。
2. **展示层五组收敛，底层 10 态保留**：待办（triage/todo/ready）→ 进行中（running）→ 待验收（review）→ 受阻（blocked/failed）→ 已完结（done/cancelled/archived）。地图 statusBucket 把 blocked/failed 从「未完成」桶里拆出单列「受阻」，避免失败卡与待办混色。
3. done→archived 提供自动策略（完成后 N 天自动归档，可在设置关闭），人工入口保留。

**优先级：P0**（第 1 条一行改动消灭强制摩擦；第 2 条 P1）。

## 二、连接方向

### 2.1 现状机制

画布上拖「＋」建的线是 **depends 依赖边**（语义：src 依赖 dst，dst 是前置，含成环检测）。前端拖线两端不校验类型（app.js:4967-5040），方向限制全在后端：**前置端必须是 task/handoff 卡**，否则 400「依赖线只能指向任务卡…它没有可完成的任务流，这条线大概率永远满足不了」（cards.js:1042-1054）。因此：

- 智能卡→任务卡（前置=任务卡）：**合法放行**；
- 任务卡→智能卡（前置=智能卡）：**被拒**。

派发边是另一类边（kind='dispatch'）：只能由派发动作产生（cards.js:2075-2076）、不可手删（2105-2106）、方向固定 task→agent、携带 dispatch_id/generation、生命周期跟 run 走（active→completed/cancelled，cards.js:806-815 / 285-298）。

### 2.2 四角度评估

| 角度 | 评估 | 结论 |
|---|---|---|
| 模型语义（谁是执行主体） | 智能卡是执行主体不是交付物，没有「可完成的任务流」；若允许任务卡→智能卡建 depends，前置永不 done，派发的依赖校验（app.js:6482-6498）会**永久卡死**该任务。后端 400 文案已准确解释这一点 | 限制**合理** |
| 数据归属 | 依赖边是规划数据（用户手建手删）；派发边是执行凭证投影（系统写、不可手删、跟工作证生命周期）。混用一条通道后「这条线是计划还是执行」无法区分，删线≠撤单，撤销语义打架 | 分离**合理** |
| 权限与角色边界 | 连线是零副作用的规划手势；派发会拉起外部进程（CLI 拉终端 / CDP 驾驶桌面软件 / 进队列），有资源成本与 CDP 单实例锁约束。二者合一则一次误拖直接拉进程 | 需要**确认门**，而不是禁止方向 |
| 交互成本 | 用户心智来自 ComfyUI 与原始口述需求「**连线即派发**」（2026-10-04 设计报告）；现状拖 task→agent 得到 400 报错，且报错只解释了依赖线规则、没接住「我其实想派发」的真实意图——这是全流程中心智落差最大的一处 | 现状**不合理**，应改手势语义 |

### 2.3 潜在问题

- **agent→task 噪音边**：该方向目前放行，但「智能卡依赖任务卡」没有明确业务含义（智能卡无 done 流），属于校验口径漏洞而非有意设计，会积累语义不明的边。
- **错误处理没接住意图**：拖线被拒只说明规则，用户下一步仍是去找「派发给…」按钮重来一次——把一次手势拆成了两段操作。

### 2.4 放宽条件（收口方案）

**不放开**「连线=建派发边」（数据归属理由不松动）；**放开**「task→agent 拖线」作为**派发意图手势**：

- 拖线落点在可派发（can_dispatch_in=1）智能卡上 → 弹派发确认层（预填目标智能体、显示通道/载体状态/队列代价黄条）；
- 用户确认 → 才真正调 `dispatch-agent`，派发边由系统画出；
- 用户取消 → 不留任何边；
- 落点在任务卡/文档卡上 → 维持现行为（建 depends）。

一次点击把交互成本还给确认门，同时兑现「连线即派发」的产品初衷。

**优先级：P0**；agent→task 噪音边治理（禁建或建时提示语义）P1。

## 三、交互优化

### 3.1 等价性判断

**「任务卡主动连接智能卡」在产品逻辑上等价于「将任务派发给目标智能卡」——这正是用户原始口述需求（连线即派发），且现有派发链路已具备承接条件。**

等价成立的前提：

1. 任务卡处于可派发状态（todo/ready 且依赖满足）；
2. 目标智能卡已配置执行通道且载体就绪（cli/cdp 查载体、queue 无载体要求，cards.js:1751-1776）;
3. **有确认步隔离误触**——连线是廉价手势、派发是昂贵动作，等价必须在「确认之后」才成立。

差异与风险：

| 维度 | 连线（声明） | 派发（动作） |
|---|---|---|
| 撤销 | 删线即撤销 | 须走 release/终态，删线≠撤单 |
| 副作用 | 零 | 工作证+租约+可能拉起外部进程 |
| 失败路径 | 无 | 有整笔回滚（卡回 ready、边 cancelled、贴条，cards.js:883-901） |

若把拖线直接当派发，用户「删线」的预期会撞上「撤单」的现实。风险：误派发、队列灌水、CDP 单实例锁冲突。**所以正确形态是：拖线=选定目标+唤起确认；确认=派发。**

### 3.2 交互流程设计

**场景 A：创建时指定**

1. 创建弹窗增加可选「派发给…」下拉（列 `/api/agents` 在线智能卡，默认「暂不派发」）；
2. 选了目标 → 点「创建并派发」：自动建卡（落 todo）→ 自动调 dispatch-agent（todo 自动升 ready，cards.js:764-768 已支持）→ SSE 反馈；
3. 状态反馈：派发边即时画出，节点标签「已领取·智能体名」（复用 app.js:4571-4590 反查）；
4. 异常处理：起 run 失败 → 卡回 ready + 卡上 ⚠ 贴条 + 大白话 toast（复用 2026-10-05 失败大白话批，app.js:2685-2698）；载体缺失 → 确认层黄条预警，允许降级为「暂不派发」仅建卡。

**场景 B：创建后追加**

1. **拖线派发**（新增）：task→agent 拖线 = 派发确认层（见 §2.4）；
2. **既有入口收敛保留**：⚡ 悬停快捷条、右键「⚡ 派发给…」、详情「🚀 交给智能体」等 7 入口统一文案为「派发给…」；确认层统一展示三件事——目标卡与通道（队列/直控/驾驶）、载体状态、任务卡依赖是否满足；
3. 依赖不满足时确认层给「🪄 补全依赖并继续派发」一键路径（复用 completeDepsThenDispatch，app.js:6597-6618）；
4. 队列通道保留代价黄条（已有，app.js:6564-6568）。

**优先级：拖线派发确认 P0（同 §2.4）；创建时指定 P1。**

## 四、创建流程

### 4.1 现状步骤（8 步）

| 步 | 动作 | 评价 |
|---|---|---|
| 1 | 点顶栏「新建卡片」或画布「＋」（app.js:2741 / 6386-6399） | ✅ |
| 2 | 弹窗选类型 kind（默认 task，含自定义类型，app.js:6407-6434） | ✅ |
| 3 | 填标题（唯一必填项） | ✅ |
| 4 | 提交 POST /api/cards → 落 **triage**，地图出现灰卡 | ⚠️ 默认值错位 |
| 5 | 点开详情补正文/优先级（PUT 二次往返，无引导） | ⚠️ 弹窗没有正文字段，二次往返必然发生 |
| 6 | **手动切状态 triage→todo**（/status 或拖带） | ❌ 整步冗余 |
| 7 | ⚡/右键「派发给…」选智能卡 | ⚠️ 与 4/6 可合并 |
| 8 | 确认弹层 → 执行 | ✅ 确认门保留 |

### 4.2 冗余与不必要输入

- 第 6 步**整步冗余**（默认值问题，见 §1.2）；
- 第 5 步位置合理但缺引导：创建弹窗无正文输入，导致每次都必然二次编辑；优先级/工作区同样后置无入口；
- 第 4 步落 triage 使第 6 步成为必然——两步是同一个 bug 的两张脸。

### 4.3 推荐步骤（4 步；「创建并派发」路径 2 步）

1. 点「＋」→ 弹窗：标题必填 + 类型默认 task + **可折叠高级区**（正文/优先级/工作区）+ **可选「派发给…」**；
2. 点「创建」（或「创建并派发」）；
3. 自动落 todo →（选了目标则）自动派发；
4. 地图即时反馈（派发边画出 / 状态色变化 / 失败贴条大白话）。

增强项（P2）：**模板/快捷创建**——card_types 档位注册表已支持自定义类型（app.js:6317-6335），可给常用类型配「标题前缀+正文骨架+默认档位」；**画布拖拽即建卡**（按住「＋」拖到空白处松手=原位建卡+行内命名）。

### 4.4 优化前后对比

| 维度 | 现状 | 改后 |
|---|---|---|
| 创建到可派发 | 6 步（含 1 次手动切状态） | 2 步（填标题→创建） |
| 创建到执行 | 8 步（建卡→切状态→找派发入口→选卡→确认） | 3 步（填标题+选目标→「创建并派发」→确认） |
| 建卡后初始态 | triage（待细化，被派发预检拦截） | todo（可直接派发） |
| 拖 task→agent 线 | 400 报错，意图落空 | 派发确认层，一次点击成交 |
| 正文/优先级 | 必然二次往返 | 弹窗可折叠高级区一次填完 |
| 失败反馈 | 卡变红+贴条+大白话 toast（已落地） | 不变，复用 |
